# gitwire-chat

**중앙 서버 없이 git 레포를 메시지 저장소로 쓰는 로컬-퍼스트 비동기 채팅.**

각 참가자가 자기 컴퓨터에서 이 앱을 띄우고, 공유 private git 레포 하나를 통해
대화한다. 서버 운영이 0이고, 네트워크는 egress(`pull`/`push`)만 쓴다.

```
   내 브라우저 ──HTTP/SSE──▶ 내 로컬 앱 ──push──▶ ┌──────────────┐ ◀──push── 상대 앱
   (localhost)                          ◀──pull── │ private repo │ ──pull──▶
                                                  └──────────────┘
```

전송 계층은 **[gitwire](https://github.com/yunhyuk-choi/gitwire)** 가 전부 담당한다. 이 앱에는 git 명령이
한 줄도 없다. gitwire 는 레코드 `payload` 안을 해석하지 않으므로, "메시지"라는
개념은 오직 여기서 정의된다.

---

## 띄우기

```bash
git clone https://github.com/yunhyuk-choi/gitwire-chat.git
cd gitwire-chat
pip install .          # 전송 계층(gitwire)은 의존성으로 함께 받아온다

python -m gitwire_chat
# → http://127.0.0.1:8770
```

레포 하나만 클론하면 된다 — [gitwire](https://github.com/yunhyuk-choi/gitwire) 를
옆에 나란히 두지 않아도 설치된다(`pyproject.toml` 의 `dependencies` 가 그 레포를
직접 가리킨다). 기반을 함께 고칠 때의 개발용 설치는 아래 「개발」 참조.

클론 없이 바로 설치해 쓸 수도 있다:

```bash
pip install "gitwire-chat @ git+https://github.com/yunhyuk-choi/gitwire-chat.git"
```

그리고 그다음부터 **갱신은 한 줄이다**:

```bash
python -m gitwire_chat update
```

돌고 있는 앱을 찾아 멈추고 · 다시 설치하고 · **원래 옵션 그대로** 다시 띄운다.
터미널을 열 필요도 없다 — 사이드바 「업데이트 확인」 → 「지금 갱신」이 이 명령을
대신 돌리고, 새 버전이 뜨면 화면이 알아서 돌아온다(그래도 **CLI 가 정본**이다 —
앱이 아예 안 뜨는 상태에서는 버튼이 없다). 자세히는 아래 「갱신은 한 줄이다」
참조. 손으로 하던 것은 이것이었다:

```bash
# 옛 절차 (지금도 동작한다 — update 가 하는 일이 이것이다)
pip install --force-reinstall --no-deps   "gitwire-chat @ git+https://github.com/yunhyuk-choi/gitwire-chat.git"
python -m gitwire_chat
```

`--no-deps` 는 바뀌지 않은 의존(Flask 등)까지 다시 받지 않게 한다. ⚠️ 그 대가로
**전송 계층 `gitwire` 도 갱신되지 않는다** — 손으로 할 때는 그것도 함께 설치해야
한다(`pip install --force-reinstall --no-deps "gitwire @ git+https://github.com/yunhyuk-choi/gitwire.git"`).
`python -m gitwire_chat update` 는 그 한 걸음을 알아서 한다 (「갱신은 한 줄이다」).

**강력 새로고침은 이제 필요 없다.** 정적 자원 URL 에 내용 도장이 박혀 있어서,
파일이 바뀌면 URL 이 바뀌고 브라우저가 알아서 새로 받는다 — 아래
「갱신하면 화면도 같이 갱신된다」 참조.

옵션:

| 옵션 | 뜻 |
|---|---|
| `--port` | 포트 (기본 8770). 바인드 주소는 `127.0.0.1` 고정이다 — 아래 「보안 모델」 |
| `--home DIR` | 로컬 상태 디렉토리 (기본은 아래 규칙) |
| `--author 이름` | 표시 이름 기본값 |
| `--poll-interval 초` | 폴 주기 (기본 15초) |
| `--no-notify` | OS 알림 끄기 |
| `--open` | 기동 후 브라우저 열기 |

서브커맨드가 둘 있다 — `autostart` (로그인 시 자동으로 띄우기: 등록·해제·상태)와
`update` (최신으로 갱신). 아래 「알림 · 자동 시작」·「갱신은 한 줄이다」 참조.

### 방 만들기 / 합류하기

1. 사이드바 `＋` → **레포 주소를 넣는다.** 빈 레포면 gitwire 가 방 규약을 심는다.
   클론은 **앱이 알아서** 한다 — 위치도 앱이 정한다(아래 「로컬 상태」). 사용자가
   `git clone` 을 칠 일도, 어디에 둘지 고민할 일도 없다.
2. 같이 대화할 사람을 그 레포의 **collaborator** 로 초대한다.
3. 상대도 자기 컴퓨터에서 이 앱을 띄우고 **같은 주소**를 넣으면 같은 방이 된다.

**레포가 아직 없다면** — 등록 폼의 「레포가 아직 없다 — 만들기 거들기」를 편다.
소유자와 레포 이름을 넣고 확인을 누르면 *무엇이 만들어지는지*(어느 계정에 어떤
이름으로, **비공개**로) 먼저 보여준다. 그 다음은 둘 중 하나다:

* **토큰이 있으면** (`GITWIRE_TOKEN` 등) → 「지금 만들기」 한 번으로 앱을 떠나지
  않고 만든다. 만들어진 주소로 **방까지 이어서 만든다** — 주소를 옮겨 적지 않는다.
* **토큰이 없으면** → GitHub 의 새 레포 폼이 **미리 채워진 링크**를 준다
  (이름·비공개 설정이 채워져 있다). 만들고 돌아와 「만들었다 · 이 주소로 방 만들기」
  를 누르면, 소유자·이름에서 유도한 주소로 방이 만들어진다.

⚠️ 레포 생성은 **계정을 바꾸는 외부 동작**이다. 계획을 보여준 뒤 사용자가 누를
때만 실행하고, 실패하면 사유(이름 중복·권한 부족·토큰 스코프)를 그대로 보여준다.
GitHub 이 아닌 호스트는 거들 수 있는 만큼만 거든다 — GitLab 은 링크만, 모르는
호스트(사내 git 등)는 주소 입력만 받는다.

### 방을 받는 동안 · 실패했을 때

방 등록은 **즉시** 끝나고 클론은 뒤에서 돈다. 그래서 큰 방이나 느린 네트워크에서도
버튼이 멈춰 있지 않다.

* 방은 목록에 **바로 뜨고** "받는 중…" 으로 표시된다. 다 받으면 대화가 저절로
  채워진다(같은 SSE 채널로 상태가 온다).
* 실패해도 **방이 사라지지 않는다.** 그 자리에 사유가 남고 「재시도」가 있다.
  사유는 구분해서 보여준다 — 주소 오류 / 인증 실패 / 없는 레포 / 네트워크.
* 비공개 레포에서 가장 흔한 실패는 토큰이다. 그때는 **어느 환경변수에 무엇을
  넣어야 하는지**까지 안내한다. (GitHub 은 접근 권한이 없는 레포를 "없는 레포"로
  답하므로, 그 안내가 두 경우 모두에 붙는다.)

private 레포라면 토큰이 필요하다. 값은 **저장하지 않는다** — 환경변수 이름만
기억한다.

```bash
# Windows PowerShell
$env:GITWIRE_TOKEN = "ghp_..."
# macOS / Linux
export GITWIRE_TOKEN=ghp_...
```

방마다 다른 토큰을 쓰려면 방 등록 시 "토큰 환경변수" 칸에 다른 이름을 넣는다.

## 로컬 상태는 어디에 쌓이나

방 클론·커서·방 목록은 전부 한 디렉토리 아래에 모인다.

```
<chat_home>/rooms.json                        방 목록 (이 앱 소유)
<chat_home>/installation.txt                  이 설치의 전송 식별자 (gitwire 소유)
<chat_home>/channels/<slug>-<hash>/clone      방 하나의 git 클론
<chat_home>/channels/<slug>-<hash>/cursors    "어디까지 읽었나" (gitwire)
```

`installation.txt` 는 **gitwire 가 만들고 관리한다.** 같은 머신에서 인스턴스를
둘 띄워도(`--home` 을 달리) 서로 다른 전송 식별자를 갖고, 재시작해도 유지된다 —
그래서 "이건 내가 보낸 것인가" 판정이 흔들리지 않는다. 이 앱이 예전에 직접 하던
일인데, 기반이 보장하므로 소비자가 다시 풀지 않는다.

`<chat_home>` 은 이 순서로 정해진다:

1. `--home` 또는 `GITWIRE_CHAT_HOME`
2. **소스 체크아웃**으로 돌고 있으면 `<레포 루트>/chats`
3. 그 외(`pip install` 로 설치한 형태 — 앱 디렉토리가 없다)는 OS 데이터 디렉토리
   (`%LOCALAPPDATA%\gitwire-chat`, `~/Library/Application Support/gitwire-chat`,
   `$XDG_DATA_HOME/gitwire-chat`)

> ⚠️ `chats/` 가 **gitignore 되어 있다는 것이 이 배치의 전제다.** 무시되면 부모
> 레포의 `git status` 에 안 보이고 `git clean -fdx` 도
> `Would skip repository ...` 로 클론을 건너뛴다. 무시되지 **않으면** 즉시
> `embedded git repository` 경고와 함께 gitlink 로 스테이징된다.
> `.gitignore` 의 `chats/` 줄을 지우지 마라. 그리고 그 줄에 **인라인 주석을
> 붙이지 마라** — gitignore 에서 `#` 는 줄 첫 칸에서만 주석이라
> `chats/  # 설명` 은 패턴 전체를 무효화한다.

### (선택) 자격증명 조회 캐시 — `GITWIRE_CHAT_CREDENTIAL_CACHE`

**기본은 꺼져 있다.** 켜려면 초 단위 수명을 준다 (예: `900`).

```bash
# Windows PowerShell
$env:GITWIRE_CHAT_CREDENTIAL_CACHE = "900"; gitwire-chat
# macOS / Linux
GITWIRE_CHAT_CREDENTIAL_CACHE=900 gitwire-chat
```

무엇을 사나 — 백그라운드 폴러가 원격을 볼 때 git 이 왕복마다 OS 자격증명
관리자를 **새 프로세스로** 띄운다. 실측(이 머신 · GitHub private repo, 5회
중앙값) `ls-remote` **1320ms → 1167ms**. 나머지 ~900ms 는 캐시로 지울 수 없는
고정비다(HTTPS 왕복 3회 + 프로세스 기동).

무엇을 파나 — `git-credential-cache` 데몬이 자격증명을 **메모리에** 그 시간 동안
들고 있고, 같은 OS 사용자로 도는 프로세스가 소켓으로 꺼내 쓸 수 있다. 디스크에는
쓰지 않는다. 짧게 잡을수록 노출 창이 좁다.

무엇을 건드리지 않나 — **사용자의 global·system git 설정을 고치지 않는다.**
이 앱이 만든 클론의 `.git/config` 에만 쓰고, 상속된 helper 는 사슬 뒤에 남겨
캐시가 비면 원래대로 동작한다.

⭐ 그리고 이건 **사람이 기다리는 경로가 아니다.** 타임라인 조회는 원격을 아예
보지 않으므로, 이 설정이 줄이는 것은 백그라운드 폴러의 비용뿐이다. 그래서
기본값이 끔이다.

## 알림 · 자동 시작

앱 프로세스는 브라우저와 **무관하게** 방을 폴링한다. 그래서 탭이 닫혀 있거나
숨겨져 있어도 새 메시지를 알고, 그때 OS 알림을 띄운다
(Windows 토스트 / macOS `osascript` / Linux `notify-send`, 전부 실패하면 로그만).
탭이 그 방을 **보고 있으면** 알림을 띄우지 않는다.

### 로그인할 때 자동으로 띄우기

알림이 제 값을 하려면 그 프로세스가 **로그인할 때 이미 떠 있어야** 한다.
명령 한 줄이다 — 안내문을 보고 따라 할 필요가 없다.

```bash
python -m gitwire_chat autostart install --dry-run   # ① 무엇을 어디에 쓸지 먼저 본다
python -m gitwire_chat autostart install             # ② 등록
python -m gitwire_chat autostart status              # 지금 등록돼 있나 · 어디에 · 로그는 어디
python -m gitwire_chat autostart uninstall           # 해제
```

OS 별로 **그 OS 의 정석 수단**을 쓴다. 셸 명령이 아니라 파일 하나를 쓰는 것이
기본이고, 서비스 관리자에게 알려야 하는 곳에서만 한 단계를 더 밟는다.

| OS | 무엇이 만들어지나 | 추가 단계 |
|---|---|---|
| Windows | 시작 폴더(`shell:startup`)의 `gitwire-chat.cmd` | 없음 (파일이 곧 등록이다) |
| macOS | `~/Library/LaunchAgents/com.github.yunhyuk-choi.gitwire-chat.plist` | `launchctl bootstrap` |
| Linux | `~/.config/systemd/user/gitwire-chat.service` | `systemctl --user enable --now` |

지키는 것들:

* **먼저 보여준다.** `--dry-run` 이 쓸 경로와 **파일 내용 전문**을 출력한다.
  실제 등록에서도 같은 것을 보여준 뒤에 쓴다 — 환경을 바꾸는 동작이 조용히
  일어나지 않는다. `--os windows|macos|linux|all` 로 **다른 OS 의 파일도 미리**
  볼 수 있다(미리보기 전용 — 실제 등록은 그 OS 에서만 된다).
* **멱등.** 두 번 등록해도 파일은 하나다. 내용이 같으면 아무것도 쓰지 않고
  "이미 등록돼 있다"고 말한다. 옵션이 바뀌었으면 그 자리를 갱신한다. 해제도
  없으면 없다고 말하고 끝난다.
* **지금 이 인터프리터를 박는다.** venv 로 설치했으면 그 venv 의 인터프리터
  **절대 경로**가 들어간다 — 로그인 셸의 `PATH` 를 믿지 않는다. `--port`·`--home`
  같은 옵션도 등록 시점 값이 그대로 파일에 들어간다.
* **콘솔 창이 뜨지 않는다.** Windows 에서는 같은 디렉토리의 `pythonw.exe` 를
  쓴다(있는지 실제로 확인하고, 없으면 `python.exe` + 최소화로 폴백하며 그 사실을
  보고한다).
* **로그가 남는다.** 백그라운드로 돌면 실패해도 화면에 아무것도 안 남으므로,
  표준출력·표준오류를 파일 하나로 모은다. `status` 가 그 경로를 알려준다.
  (`%LOCALAPPDATA%\gitwire-chat\logs\` / `~/Library/Logs/gitwire-chat/` /
  `$XDG_STATE_HOME/gitwire-chat/logs/`)
* **systemd 가 없는 Linux 에서는 명확히 실패한다.** 조용히 다른 수단으로
  넘어가지 않고, 수동 방법을 안내한다 — 등록됐다고 믿게 만드는 것이 제일 나쁘다.

> ⚠️ Windows 의 시작 폴더에는 감독자가 없다. `uninstall` 은 **다음 로그인부터**
> 뜨지 않게 한다 — 지금 떠 있는 프로세스는 그대로 돈다(작업 관리자에서
> `pythonw.exe` 를 끝내면 된다). macOS·Linux 는 `bootout`/`disable --now` 로
> 그 자리에서 함께 내린다.

**Windows 에서 작업 스케줄러를 쓰지 않는 이유** — 스케줄러에도 "로그온 시 실행"
트리거가 있다. 하지만 등록 수단이 `schtasks`/XML(UTF-16)이라 셸·인코딩 의존이
늘고, 사용자가 눈으로 확인·삭제하기 어렵다. 시작 폴더는 탐색기에서 바로 보이고
파일을 지우면 끝난다. 스케줄러가 주는 추가 능력(지연·조건·재시도)은 "로그인하면
뜬다"는 목적에 필요하지 않다.

#### 수동으로 하려면

자동 등록이 막히는 환경이 있다(정책으로 시작 폴더가 잠긴 경우, systemd 없는
배포판, 읽기 전용 홈 등). 그때는 아래를 손으로 한다 — `autostart install
--dry-run` 이 출력하는 내용을 그대로 붙여 넣으면 된다.

* **Windows** — `Win+R` → `shell:startup` → 아래 내용의 `.cmd` 파일을 넣는다.
  (또는 작업 스케줄러 → 새 작업 → 트리거 "로그온할 때" → 동작에 같은 명령)
  ```bat
  @echo off
  start "" /b "C:\경로\pythonw.exe" -m gitwire_chat --port 8770
  ```
* **macOS** — `~/Library/LaunchAgents/` 에 `.plist` 를 만들고
  `launchctl bootstrap gui/$UID <plist 경로>` (`ProgramArguments` 에
  `python3 -m gitwire_chat`).
* **Linux (systemd --user)** — `~/.config/systemd/user/gitwire-chat.service`
  를 만들고 `systemctl --user enable --now gitwire-chat`.
* **systemd 가 없으면** — 데스크톱 환경의 "시작 프로그램"에 등록하거나
  `~/.xprofile` 에 같은 명령을 백그라운드(`... &`)로 넣는다.

> 등록 파일을 둘 디렉토리는 `--dir`(또는 `GITWIRE_CHAT_AUTOSTART_DIR`)로 바꿀 수
> 있다. 실제 시작 폴더를 건드리지 않고 시험해 보거나 테스트할 때 쓴다.

## 메시지는 어떻게 생겼나

gitwire 봉투와 이 앱의 payload 는 **역할이 겹치지 않게** 나눠 담는다.

| 무엇 | 어디 | 왜 |
|---|---|---|
| 메시지 ID·정렬 키 | 봉투 `id` | 이미 유일하고 정렬 가능하다. 새로 만들 이유가 없다 |
| 표시 시각 | 봉투 `ts` | git 호스트 기준 **공통 시계**. 로컬 시계보다 정확하다 |
| 발행 설치본 | 봉투 `sender` | 전송 식별자(IP 에 가깝다). 표시용이 아니다 |
| 표시 이름 | payload `author` | 한 사람이 프로세스를 둘 쓸 수 있다 |
| 본문 | payload `text` | |
| 답장 대상 | payload `reply_to` | 봉투 `id` 를 가리킨다 |
| 종류·버전 | payload `kind`·`v` | append-only 라 나중에 고칠 수 없다 |

레포에 실제로 쌓이는 파일 한 건:

```json
{"gitwire":1,"id":"records/20260903/20260903T041210032Z-alice@example.com.a3f9c1-f96bb4.json",
 "sender":"alice@example.com.a3f9c1","ts":"2026-09-03T04:12:10.032Z",
 "payload":{"kind":"msg","v":1,"author":"앨리스","text":"안녕"}}
```

### 「내 것」은 봉투로 판정한다

말풍선이 오른쪽(내 것)에 붙을지는 **봉투 `sender` 와 이 설치본의 식별자를
비교**한 결과다. 서버가 JSON 을 만들 때 `mine` 필드로 실어 보내고
(`RoomManager.is_mine` — 이 비교를 하는 곳은 코드 전체에서 여기 하나다),
화면은 그 값을 그릴 뿐 스스로 다시 판정하지 않는다.

서버에서 판정하는 이유는 **모든 경로가 그 한 곳을 지나기 때문**이다 — 최초
로드·위로 페이징·검색·SSE·전송 응답이 전부 같은 직렬화를 탄다. 브라우저에서
판정하려면 자기 sender 를 내려보내는 배관이 하나 더 필요하고, 그 배관이 빠진
경로가 곧 버그가 된다. 실제로 그랬다: 예전에는 `mine` 을 **전송 직후에만**
손으로 참으로 박아서, 새로고침하면 내가 쓴 말이 **전부** 왼쪽(남의 것)으로
넘어갔다. 봉투에는 답이 다 있는데 아무도 비교를 하지 않았던 것이다.

예외는 하나다 — 아직 봉투가 없는 **낙관적 항목**(`~pending/…`). 방금 이
입력칸에서 나왔으니 정의상 내 것이고, 봉투가 도착하는 순간 서버 판정이 그
자리를 대신한다.

⚠️ 판정 단위는 **사람이 아니라 설치본**이다. 자세히는 「정직한 한계」.

## 읽음 표시 — 두 기능이고 성격이 다르다

카톡처럼 두 가지를 보여준다. 같아 보이지만 **누구 것인가**가 달라서, 저장 위치도
발행 여부도 반대다.

| | ① 방 목록의 **내가 안 읽은 개수** | ② 방 안의 **남이 안 읽은 수** |
|---|---|---|
| 누구 것 | 나 | 남 (참가자 전체) |
| 발행 | **없다** — 내 컴퓨터에만 있으면 된다 | 필요하다 (남이 알아야 한다) |
| 저장 | 채널 디렉토리의 로컬 커서 (`cursors/read.json`) | 공유 레포의 `participants/<사람>.json` |
| 비용 | git 왕복 0 · **git 호출 0** (캐시된 나열) | 폴 주기마다 캐시된 나열 1회 |
| 어디에 보이나 | 방 목록 뱃지 (방 **안**에는 없다) | 메시지마다 작은 숫자 |

①에 발행이 없는 이유는 단순하다 — **내 읽은 위치를 남이 알 필요가 없다.** 그리고
방 **안**에 내가 안 읽은 개수를 띄우지 않는 이유도 같다: 보고 있는 동안은 내가
읽었다는 것을 내가 이미 안다.

### ⭐ 카운트를 메시지마다 저장하지 않는다 — 커서에서 파생시킨다

```
메시지 M(작성자 A) 의 카운트 = |{ p ∈ 참가자, p ≠ A, cursor(p) < M }|
```

* 상태가 **O(사람 수)** 다. 메시지가 몇만이어도 늘어나지 않는다.
* 누군가의 커서가 전진하면 **그 아래 메시지들의 카운트가 한꺼번에 줄어든다.**
  저장값이라면 메시지마다 숫자를 갱신해야 하고, 그 갱신 하나하나가 append-only
  레포에 쓰는 일이라 개수만큼 커밋이 생긴다. 실측으로 확인한다: 커서를 한 번
  전진시키면 원격에 커밋이 **1개** 늘고 그 아래 4건의 카운트가 전부 0 이 된다
  (`tests/test_two_instances.py`).
* 카운트라는 숫자는 **어디에도 저장되지 않는다.** 서버는 커서 지도만 주고
  (`GET /api/rooms/<id>/reads`), 계산은 화면이 한다 (`static/js/reads.js` —
  공식의 유일한 원천이다. 2-인스턴스 실측도 파이썬에 공식을 베끼지 않고
  **그 모듈을 node 로 불러** 카운트를 얻는다).

### 저장 = 사람당 파일 하나 (레코드가 아니다)

발행되는 커서는 기반의 **참가자 상태 예약 경로**에 쓴다 (gitwire README
「참가자별 가변 상태」).

```json
participants/yh.choi@example.com.json
{"gitwire_state":1,"key":"yh.choi@example.com","identity":"yh.choi@example.com",
 "updated_at":"2026-09-08T12:18:21Z",
 "value":{"kind":"read-cursor","v":1,
          "cursor":"records/20260908/…json","senders":["yh.choi@example.com.a3f9c1"]}}
```

* **레코드로 발행하지 않는다.** append-only 로 적으면 그 사람의 *현재* 커서를
  알기 위해 마지막 read 레코드까지 **과거로 스캔**해야 한다 — 2주 안 읽은
  사람이면 2주치다. keyset 페이징으로 없앤 전량 스캔이 그대로 되살아난다.
* **공유 파일 하나에 전원의 커서를 넣지 않는다.** 두 사람이 같은 순간 읽으면
  같은 경로를 같이 써서 매번 충돌한다. 사람당 파일이면 **경로마다 쓰는 사람이
  한 명**이라 충돌이 구조적으로 불가능하다 (실측: 두 사람이 같은 순간 읽고 push
  → 둘 다 반영, 충돌 0).
* `senders` 는 그 사람의 **설치본 목록**이다. 봉투에는 사람 키가 아니라 설치본
  식별자만 있으므로, 카운트 공식의 `p ≠ A`(작성자 제외)를 판정할 근거가 이것뿐이다.

### 식별자는 `git user.email` — **사람** 단위다

설치본 식별자(`sender`)를 쓰면 한 사람이 노트북·데스크탑을 함께 쓸 때 **참가자
2명**으로 세어져 카운트가 0 이 되지 않는다. 그래서 사람 단위 키를 쓴다 — 기반이
이미 `git config user.email` 을 안다.

같은 사람의 두 기기는 **같은 파일**을 공유하므로 값이 `max` 로 합쳐진다(쓰기 전에
저장된 값을 읽는다). 그 한 경우에만 경로가 겹치고, 그때의 push 경합은 기반이
해소한다 — 그리고 그것이 **대화를 막지 않는다**는 것을 실측으로 확인한다.

git 신원이 없는 환경(컨테이너 등)은 `GITWIRE_CHAT_PERSON` 으로 직접 줄 수 있다.
아무것도 없으면 설치본 식별자로 떨어지고 **그 사실을 로그에 남긴다**(조용히 열화
하지 않는다).

### 참가자 집합 = 커서 파일 집합

분모를 아는 방법이 그것뿐이다. 그래서 **방을 열 때** 내 커서 파일이 없으면
만든다 (로컬 stat 한 번, 없을 때만 쓴다). 설치 스크립트에 넣지 않는 이유:
나중에 추가한 방을 놓친다.

**유령 참가자는 그냥 센다.** 설치했지만 앱을 안 켜는 사람의 커서는 움직이지
않고, 그러면 카운트가 영구히 ≥1 로 남는다 — **그게 사실이다.** 오래 안 움직인
커서를 분모에서 빼면 조용히 "다 읽음"이 되는데 그게 더 나쁘다.

### 커서가 전진하는 시점 — "탭이 열림"이 아니라 "화면에 들어옴"

* 가상 스크롤이 **어느 항목이 창 안에 있었는지** 알고 있다. 그 최대값이 기준이다
  (타임라인이 그것을 알려 주고, 읽음 모듈이 **디바운스**해서 발행한다 — 스크롤
  한 번에 push 를 만들지 않는다).
* **탭이 안 보이면 읽은 것으로 치지 않는다.**
* 내가 **보낸** 말은 내가 읽은 말이다 — 커서가 그 자리까지 간다. 그래서 남의
  화면에서 내가 그 메시지를 안 읽은 사람으로 세어지지 않는다.
* 커서는 **단조 증가**한다. 뒤로 가면 카운트가 *늘어나* 사람 눈에 고장으로
  보이므로, 되돌리는 길을 아예 두지 않는다 (항상 `max`).

### 발행은 best-effort 이고 메시지에 양보한다

읽음 push 가 메시지 전송을 막으면 최악이다. 그래서 발행은 **파일을 쓰는 것까지**
이고, 밀어내기는 이미 있는 아웃박스가 한다 (`outbox.py` — 배칭·백그라운드 push).
대기 중인 메시지와 **한 커밋**으로 나가므로 순서가 뒤집힐 여지도 없다. 아웃박스의
`pending`(아직 못 나간 **말** 건수)은 오염시키지 않는다 — 읽음은 메시지가 아니다.

내 쪽 화면은 **낙관적**이다: 내가 읽는 순간 뱃지와 카운트가 즉시 줄고, 발행은
뒤에서 나간다.

### ⚠️ 지연은 구조적이다 (우회로가 없다)

```
상대가 읽음 → 상대의 push → 내 폴링(기본 15초) → 내 화면의 숫자가 줄어든다
```

그래서 **숫자가 30초쯤 늦게 줄어든다.** 이건 버그가 아니라 이 구조의 값이다 —
중앙 서버가 없으므로 상대가 우리를 깨워 줄 방법이 없고, 폴 주기를 줄이면 그만큼
요청이 늘어난다. 감추지 않고 사실로 적는다.

읽음 커서는 **레코드가 아니라서** 상대가 읽기만 하면 새 메시지가 0건인 커밋이
올라온다. 그런 변화를 알아채는 것은 폴링의 **틱 훅**이다(기반이 폴 한 틱이
끝났음을 알려 준다) — 그래서 원격을 보는 스레드가 하나 더 늘지 않는다.

### 화면이 지키는 것

* 카운트는 **시간에 따라 변하는 파생값**이라 "보내는 중/실패"처럼 **같은 노드
  위에 덧입힌다** — 노드를 다시 만들지 않는다 (`rebuiltInView` 0).
* 그 자리는 **자리를 차지하지 않는다**(절대 위치 + 미리 비워 둔 오른쪽 여백).
  숫자가 붙거나 떨어질 때 높이가 바뀌면 가상 스크롤이 그 항목을 매번 다시 재야
  하고, 카운트는 자주 바뀌므로 그 재측정이 상시 비용이 된다.
* '여기부터 새 메시지' 구분선은 반대로 **자리를 차지해도 된다** — 방을 열 때 한
  항목에 한 번만 붙기 때문이다. 그때는 그 항목 하나만 다시 잰다(머리 숨김과 같은
  규율). 그리고 내가 다 읽어도 **눈앞의 구분선은 사라지지 않는다** — 어디까지가
  새 것이었는지의 표식이기 때문이다.
* 세 배치(말풍선·`log`·`ide`)와 모든 팔레트에서, **320px 에서도** 보인다는 것을
  진짜 브라우저가 계산한 값으로 확인한다 (`tests/test_browser_smoke.py`).

## 보내기는 원격을 기다리지 않는다

Enter 를 누르고 **2.7~3.4초**가 걸렸다. 원인은 하나였다 — 전송이
`channel.append(payload, flush=True)` 를 불렀고, `flush=True` 는 *즉시 커밋 +
push* 라서 HTTP 응답이 GitHub push 를 통째로 기다렸다(자격증명 관리자 ~1.3초 +
HTTPS 왕복).

그런데 **내구성은 push 가 주는 것이 아니다.** 기반(gitwire)의 `Channel.append`
도크가 이미 이렇게 말한다 — "파일은 즉시 디스크에 쓰이고(내구성), 커밋·push 는
배칭 창 안의 여러 건을 묶어 한 커밋으로 나간다." 즉 `flush=True` 는 안전한 쓰기
위에 **동기 네트워크**를 한 겹 얹은 것뿐이었다. 그 겹을 응답 밖으로 옮겼다:
`src/gitwire_chat/outbox.py` 가 방마다 워커 하나를 두고 밀어낸다.

**유실은 무엇이 막나** — 세 겹이다. ① `append` 가 파일을 **디스크에** 쓰는 것이
내구성의 전부다(그 뒤는 전달 문제다). ② 앱이 **강제 종료돼도** 그 파일은 작업
사본에 남고, 다음 기동에 아웃박스가 한 번 밀면 기반이 그것을 먼저 커밋한 뒤
push 한다. ③ 정상 종료는 접기 전에 한 번 더 민다. 실측(진짜 GitHub 원격):
보낸 직후 `kill` → 원격에 없음 → **재기동 → 원격 도달**.

**실패는 조용하지 않다** — push 가 실패하거나 20초가 지나도록 못 나가면 방 상태가
`stuck` 이 되고, 그 사실이 SSE(`outbox` 이벤트)와 방 목록에 함께 실려 입력창 위
띠로 뜬다(사유 + 건수 + 「다시 보내기」). 그동안에도 레코드는 로컬에 그대로 있고
지수 백오프로 계속 재시도한다. 문구 설계는 위 「화면이 지키는 것」의 표.

**순서** — 방당 워커가 하나라 push 가 겹치지 않고, 레코드 파일 이름이 고정폭
타임스탬프라 원격 정렬(=표시 순서)이 커밋을 어떻게 쪼개든 시간순이다.
실측: 연달아 5건 → 원격 `ls-tree` 정렬 순서가 보낸 순서와 일치.

### 실측 (진짜 GitHub 원격 · `POST /api/rooms/<id>/messages` · HTTP 201 확인)

| | 1번째 | 2~6번째 (중앙값) |
|---|---|---|
| 이전 (`flush=True`) | 2816 ms | **2828 ms** |
| 지금 (아웃박스) | 223 ms | 2864 ms ⚠️ |
| 지금 + 기반 한 줄 수정 | 74 ms | **24 ms** |

⚠️ **아직 절반이다 — 기반(gitwire)에 한 곳을 고쳐야 끝난다.**
`Channel.flush()` 가 **네트워크 push 를 채널 락 안에서** 한다. 그 락은
`append()`·읽기·`sync()` 가 함께 쓰므로, 배경 push 가 도는 2.7초 동안 *다음
보내기와 조회가 통째로 줄을 선다.* 그래서 첫 건만 빨라지고 이어지는 건은 그대로다.
`sync()` 는 이미 같은 문제를 "락은 로컬을 바꾸는 동안만 쥔다"로 풀어 뒀다 —
`flush()` 만 그 규율 밖에 있다. 위 표의 셋째 줄은 그 한 줄을 옮겼을 때의 실측이다.

조회도 같은 자리에서 갈린다 (push 와 **동시에** 건 `GET /messages`, 6초간 반복):

| | 중앙값 | 최대 |
|---|---|---|
| 이전 | 56~62 ms | 2805~3013 ms |
| 지금 (아웃박스) | 69~84 ms | 2900~4064 ms |
| 지금 + 기반 한 줄 수정 | 64~73 ms | **707~938 ms** |

즉 이 변경이 조회를 **더 막지는 않는다**(중앙값 그대로). 남은 꼬리는 전부
기반의 락이다.

## 화면이 지키는 것

* **타임라인을 통째로 다시 그리지 않는다.** 서버는 HTML 을 한 번만 주고, 이후엔
  SSE 로 온 JSON 한 건마다 노드를 만들어 붙이기만 한다. **화면 안에 있는** 노드는
  다시 만들지 않는다(`innerHTML` 을 쓰지 않는다 — 덤으로 XSS 봉쇄).
* **가상 스크롤이다.** 대화가 수천 건이어도 **보이는 만큼만** DOM 에 둔다
  (실측: 2000건 대화에서 DOM 노드 9~18개, 스크롤해도 그대로).
  엔진은 [@tanstack/virtual-core](https://tanstack.com/virtual)(MIT)를 레포에
  **벤더링**해 쓴다 — 빌드 단계가 없고 CDN 도 쓰지 않으므로 오프라인에서도 뜬다.
  * **높이는 실측한다.** 메시지 길이가 제각각이라 고정 높이 가정이 성립하지 않는다
    (`measureElement`). 창 크기가 바뀌면 다시 잰다.
  * 화면 밖 노드를 걷어내는 것은 **정상 동작**이다. 그래서 "리렌더 사고"와 구분해
    센다 — `recycled`(정상) vs `rebuiltInView`(**항상 0**이어야 하는 사고).
    테스트에는 일부러 사고를 내는 **대조군**이 있어 이 구분이 살아 있음을 확인한다.
  * 검색은 영향을 받지 않는다 — 서버가 **레코드 파일**을 뒤지므로 DOM 에 없는
    과거도 그대로 찾는다.
  * **가상화가 안 되면 결함으로 드러난다 — 조용히 느려지지 않는다.**
    한때 여기에 격하(degrade, 전부 그리기 폴백)가 있었지만 걷어냈다. 가상 스크롤은
    성능 때문에 붙인 기능이고, 폴백은 그 기능이 **빠진 채로** 앱이 돌게 만든다 —
    다음에 벤더를 갱신하다 또 깨지면 아무도 모르고 느린 채팅을 쓴다. 지금은
    상태줄·대화 자리·콘솔 **세 곳**에 결함이 뜨고, 그 실패는 **타임라인 모듈에만
    갇힌다**(사이드바·＋·검색은 그대로 동작한다 — 아래 「화면은 모듈로 갈라져 있다」).
* **조용한 실패는 금지다.** 스크립트에서 처리되지 않은 예외가 나면 상태줄에 뜬다
  (`error` · `unhandledrejection`). 이 앱을 쓰는 사람은 개발자 콘솔을 열지 않는다 —
  콘솔에만 남는 예외는 "아무 일도 안 일어나는 앱"과 구분되지 않는다.
  그 안내는 일상적인 상태 갱신으로 지워지지 않는다.
* **방 상태가 화면에 있다.** 받는 중·실패(사유)·재시도가 방 목록과 대화 자리에
  같이 보인다. 상태는 방 목록을 미는 기존 SSE 이벤트에 얹혀 온다(새 배관 없음).
* **위로 스크롤하면 과거가 이어 붙는다.** 페이지 버튼이 아니다. 위 끝에 가까워지면
  (`IntersectionObserver`) 다음 쪽을 자동으로 가져와 앞에 끼운다.
  * 끼우기 **전** 높이를 재고 늘어난 만큼 `scrollTop` 을 보정한다 → **읽던 자리가
    튀지 않는다.** (`overflow-anchor` 는 브라우저마다 달라 믿지 않고 꺼 둔다.)
  * 로딩 중에는 관찰을 끊는다 → 트리거가 연달아 발화해도 **요청은 한 번**이다.
  * 맨 위에 닿으면 조용히 멈춘다("대화의 시작").
* **보낸 말은 즉시 뜬다 (낙관적 업데이트).** 서버 응답을 기다리지 않는다 —
  Enter 를 누른 순간 말풍선이 흐리게("보내는 중…") 붙고, 서버가 실제 레코드를
  주면 **같은 노드의 키만** 진짜 봉투 ID 로 갈아 끼운다(노드를 다시 만들지
  않는다 — `rebuiltInView` 는 여전히 0). 실패하면 그 자리에 **"보내지 못했다" 와
  재시도**가 붙고 **글은 말풍선 안에 그대로 남는다**(입력칸으로 되돌리면 같은
  글이 두 곳에 생긴다). 응답보다 폴링(SSE)이 먼저 도착해도 같은 말이 두 줄로
  뜨지 않는다.
* ⭐ **"보냈다"는 두 사건이다 — 그래서 표시도 둘이다.** 전송 응답이 원격 push 를
  기다리지 않게 되면서(아래 「보내기는 원격을 기다리지 않는다」) 말풍선의 표시와
  방 단위 표시가 서로 다른 사실을 말한다:

  | 어디 | 무엇을 말하나 | 언제 보이나 |
  |---|---|---|
  | 말풍선 `보내는 중…` / `보내지 못했다` | **앱이 이 말을 받았나** (POST 한 번) | 실패하면 어디에도 기록되지 않은 것이다 — 그 자리에서 재시도 |
  | 입력창 위 띠 | **내 기기를 떠나 상대에게 갔나** (git push) | **못 갔을 때만.** 나가는 중은 정상 경로라 띄우지 않는다 |

  띠를 *나가는 중*에도 띄우지 않는 이유: 정상 경로가 매번 경고를 띄우면 사람이 곧
  무시하게 되고, 그러면 진짜 사고도 같이 묻힌다. 못 갔을 때는 사유와 건수, 그리고
  **"내 기기에는 남아 있다"** 를 함께 말한다 — 그래야 사용자가 같은 말을 다시
  쓰지 않는다.
* **위로 읽는 중에 온 새 메시지가 자리를 뺏지 않는다.** 맨 아래에 붙어 있을 때만
  따라 내려가고, 위에 있으면 "새 메시지 N건 ↓" 표시만 띄운다.
* 좁은 창에서는 방 목록/대화가 한 화면씩 전환된다.

## 색 테마

사이드바 머리의 **◐** 를 누르면 팔레트를 고를 수 있다. 고르는 즉시 바뀌고
(새로고침을 요구하지 않는다), 선택은 이 기기에 남는다.

| 이름 | 성격 |
|---|---|
| **기본** | 지금까지의 모습. **시스템의 라이트/다크를 따른다** (첫 방문 기본값) |
| **log** | 로그 뷰어 — 중성 어두운 회색 |
| **ide** | 에디터 통합 터미널 — 가장 얌전하고 장시간 가독성이 좋다 |
| **tty** | 인광 초록 콘솔 — 내 말이 더 밝다 |
| **tui** | tmux 계열 — 파란 강조 블록 |

터미널 팔레트는 **전부 다크 계열**이다. 고른 순간 그 색으로 가고, 억지 라이트
대응을 만들지 않는다. `기본` 만 시스템을 따른다.

### 배치도 고를 수 있다 (색과 **다른 축**이다)

같은 패널의 「배치」에서 고른다. 색과 배치는 직교한다 — `log` 배치에 `ide` 팔레트를
쓰는 조합이 성립하고, 저장값도 루트 표식도 둘로 나뉘어 있다.

| 배치 | 모습 |
|---|---|
| **말풍선** | 지금까지의 모습 — 좌우로 갈린 말풍선 (기본값) |
| **log** | 줄 기반 — **시각 · 발신자 · 본문** 3열. 로그처럼 훑어 읽는다 |
| **ide** | **연속 발화 묶기** — 같은 사람이 이어 말하면 이름·시각을 한 번만 찍는다 |

`log` 배치의 규칙:

* **시각은 `tabular-nums`, 초까지.** 자릿수가 세로로 맞아 눈이 흐르지 않는다.
* **발신자마다 고유 색** (6슬롯, 이름에서 계산 — 같은 사람은 언제나 같은 색).
  이름 글자가 그대로 보이므로 색은 **덧붙는 단서**다. 색만으로 구분하게 만들지
  않았다(색각 이상·흑백 출력에서도 읽힌다).
* **내 말은 왼쪽 레일 + 옅은 바닥.** 오른쪽으로 옮기지 않는다 — 줄 기반에서
  좌우 배치는 성립하지 않는다.
* **줄무늬(홀짝)는 모델 인덱스 기준이다.** `:nth-child` 로 칠하면 가상 스크롤이
  노드를 걷어내고 다시 붙일 때 DOM 순서가 모델 순서와 어긋나 **스크롤할 때마다
  홀짝이 뒤집힌다.** 그래서 타임라인이 모델 인덱스를 `data-row` 로 찍고 CSS 는
  그 값만 본다(인덱스는 이미 모델에 있어 추가 배관이 없다).
* **320px**: 3열이 성립하지 않으므로 본문을 아랫줄로 접어 2열이 되고, 시각은
  분까지만 보인다(초 조각만 CSS 가 숨긴다 — JS 가 폭을 재지 않는다).
* 답장 인용·"보내는 중"·전송 실패·재시도·아웃박스 띠가 **전부 그대로** 산다
  (말풍선과 같은 조각을 쓰고, 상태를 덧입히는 함수도 하나다).

### `ide` 배치 — 핵심은 배치가 아니라 **묶기**다

같은 사람이 연달아 말하면 **발신자 머리를 한 번만** 찍고 아래로 묶는다. 반복되는
이름·시각이 사라져 세로 밀도를 벌고, 대화의 결이 남는다. 내 말은 **왼쪽 레일
색만** 바뀐다 (오른쪽으로 옮기지 않는다 — 가장 절제된 구분).

⭐ **묶기는 배치 문제가 아니라 가상화 단위 문제다.** 세 갈래 중 하나를 골랐다:

* ✗ **가상화 단위를 「묶음」으로 바꾸기.** 두 곳에서 깨진다. (1) 묶음 크기에
  **상한이 없다** — 한 사람이 연달아 200건을 쓰면 그게 항목 하나이고, 3건을
  보이려고 200건을 그리게 된다(가상화가 무의미해진다). (2) 위로 불러올 때 묶음이
  **합쳐진다** — 과거 배치의 마지막 발신자가 현재 첫 메시지와 같으면 두 묶음이
  하나가 되어 항목 경계·인덱스·키가 흔들린다. 그 위에 '위로 불러오기' 커서가
  얹혀 있다.
* ✓ **단위는 메시지로 두고, 머리를 「첫 메시지의 속성」으로.** 각 메시지가
  `head`(머리를 찍나)를 갖는다. **가상화는 손댈 것이 없다** — 단위가 그대로
  메시지다. 무효화 경계도 명확하다: 새 메시지가 와도 그 항목만 계산되고, 과거를
  불러오면 **기존 첫 메시지 하나**가 머리를 잃어 그 항목 하나만 높이를 다시 잰다.
* ✓ **거기에 떠 있는 머리(sticky)를 얹는다.** 위 방식의 유일한 결함이 "창이 묶음
  **중간**에서 시작하면 머리가 화면 밖 → 누가 말했는지 모른다"다. 화면 상단에 현재
  묶음의 발신자를 띄워 그것만 해결한다(Slack 의 날짜 구분선·iOS 섹션 헤더 방식).
  **오버레이라 높이 측정에 영향이 없다** — 높이 0 의 sticky 상자 안에 절대 위치로
  얹혀 흐름을 차지하지 않는다(차지하면 가상화의 세로 좌표와 실제 픽셀이 어긋난다).
  화면 위 항목이 자기 머리를 갖고 있으면 뜨지 않는다(중복이 더 나쁘다).

**누가 무엇을 아는가**가 이 구현의 전부다:

* **머리를 찍을지 정하는 것**은 모델을 소유한 `timeline.js` 다 — 직전 메시지와
  비교하는 일이라 상태가 필요하고, `message-node.js` 는 상태 없는 변환만 한다는
  성질을 깨지 않는다.
* **머리를 어떻게 그릴지**는 `message-node.js` 의 구조 표(`STRUCTURES`)와 그
  옆의 두 표(묶는 구조인가 · 항목 간격)가 안다. 타임라인은 이름으로 **조회만**
  한다 — 구조 분기가 그쪽으로 새지 않는다.
* 머리는 **DOM 에 항상 있고 숨을 뿐**이다. 묶음이 이어져 머리를 잃을 때 노드를
  다시 만들면 `rebuiltInView` 가 깨지므로, 같은 노드 위에서 숨김만 바꾼다.

**시간 컷오프는 10분이다.** 없으면 어제 마지막 말과 오늘 첫 말이 한 묶음이 된다 —
머리를 한 번만 찍는다는 것은 "그 시각 하나가 묶음 전체를 대표한다"는 말이고,
대표할 수 없을 만큼 벌어지면 그 표기가 거짓이 된다. 값의 근거:

* 이 앱의 왕복은 실시간 타이핑이 아니다 — 원격 git 을 **폴링**해서(기본 15초)
  받는다. 한 사람이 이어 말하는 사이도 수십 초~수 분으로 벌어진다. Slack 이 쓰는
  5분을 그대로 가져오면 한 호흡의 발화가 중간에서 갈린다.
* 반대로 30분·1시간으로 늘리면 오전 묶음과 오후 묶음이 붙어, 머리에 찍힌 시각이
  아래 줄들이 실제로 말한 시간과 전혀 달라진다.
* ⚠️ 컷오프만으로 **날 경계**는 막히지 않는다(23:59 와 00:01 은 2분 차이다).
  그래서 **날이 다르면 간격과 무관하게** 새 머리를 찍는다. 같은 이름이어도
  내것/남의것이 갈리면 역시 새 머리다(표시 이름은 겹칠 수 있다).

**320px**: 묶기는 좁은 폭에서 **오히려 이득이 크다** — 반복되는 이름이 세로를 덜
먹는다. `log` 처럼 접을 것도 없어(3열이 아니다) 여백만 줄인다. 답장 인용·"보내는
중"·전송 실패·재시도·아웃박스 띠는 다른 배치와 **같은 조각**을 쓰므로 그대로 산다.

수치 증명은 `tests/js/render.test.mjs`(머리 잘림 → 떠 있는 머리 · 과거 이어짐 →
**항목 하나만** 재측정 · 한 묶음 400건에서 DOM 노드 11~18개 · `rebuiltInView` 0)와
`tests/test_browser_smoke.py`(묶인 줄 머리 `display:none`·높이 0 · sticky 높이 0 ·
팔레트 5종 × `ide` 콘솔 예외 0)가 나눠 갖는다.

### 배치 전환은 새로고침으로 간다 (색은 즉시)

색은 토큰이라 즉시 바뀌지만, 배치는 **구조**를 갈아끼운다. 즉시 전환하면 세 위험을
한꺼번에 안는다: (1) 가상 스크롤의 높이 측정값이 통째로 낡고 (2) 그걸 맞추려면
창 안 노드를 다시 만들어야 하며(= `rebuiltInView` 0 이 깨진다) (3) 픽셀 스크롤
위치가 의미를 잃는다. 새로고침이면 **세 위험이 존재조차 하지 않는다.**

읽던 자리는 잃지 않는다 — 픽셀이 아니라 **앵커 메시지 id** 로 남겼다가 복원한다
(구조가 바뀌면 픽셀은 의미가 없다). 앵커는 한 번만 쓰고 지운다.

⚠️ **망가진 테마가 스스로를 못 벗어나는 함정**을 막아 뒀다. 테마 초기화가 실패하면
루트 표식을 걷어내 **기본으로 떨어지고**, 그 사실이 상태줄·콘솔에 남는다(조용히
떨어지면 적용된 줄 알고 계속 쓴다). 고르는 칸은 대화 영역 **밖**(사이드바)에 있어
배치가 무엇이든 살아 있다. 저장된 이름이 없는 배치일 때도 같은 폴백을 탄다.

### 실제 작업은 토큰화였다

팔레트를 추가하는 일 자체는 값을 적는 일이고, 어려운 쪽은 **색이 한 군데도 박혀
있지 않게 하는 것**이다. 하나라도 남으면 그 부분만 테마를 안 따라가고, 그게
정확히 **가장 눈에 잘 띄는 버그**가 된다 (어두운 화면에 흰 띠 하나).

* `style.css` 에 색이 적혀 있는 곳은 **팔레트 구역 하나**뿐이다
  (`/* PALETTE:BEGIN */` ~ `END`). 그 밖은 전부 `var(--…)` 다.
* 토큰 이름은 **역할**이다 — `--bg` · `--panel` · `--ink` · `--muted` ·
  `--mine` · `--theirs-ink` · `--danger` · `--warn-bg` · `--focus` …
  `--green-500` 같은 색 이름은 금지다. 팔레트를 갈면 그 이름이 곧 거짓말이 된다.
* 적용은 루트 요소의 `data-chat-theme="log"` 한 줄이다. 토큰이 상속돼 내려간다.
* `기본` 은 **속성을 지운다** — 그래야 `prefers-color-scheme` 이 다시 일한다.

`tests/test_theme.py` 가 매 실행 기계로 확인한다: 팔레트 밖 색 리터럴 **0개**
(JS·템플릿 포함) · 팔레트마다 **같은 토큰 집합**(하나 빼먹으면 그 자리만 다른
팔레트 색이 새어 나온다) · 팔레트 블록에 **색 아닌 선언 없음** · 목록이
CSS·템플릿·모듈 **세 곳에서 같음** · 그리고 **대비**.

### 테마를 바꿔도 화면을 다시 그리지 않는다

색은 CSS 토큰으로 흐른다. 그래서 테마 전환은 DOM 을 **하나도** 건드리지 않는다 —
메시지 노드 재생성 0(`rebuiltInView` 0), 높이 재측정 0, `scrollTop` 그대로.
읽던 자리를 잃지 않는다. (수치 증명: `tests/js/render.test.mjs` 의
「테마를 바꿔도 메시지 노드를 다시 만들지 않는다」.)

⚠️ 그래서 팔레트에는 **색만** 넣는다. 폰트·행간·여백을 함께 바꾸면 높이가 달라져
가상 스크롤의 측정값이 낡고, 그 순간 스크롤이 튄다. 그 경계도 테스트가 지킨다.

### 접근성

* 본문 대비는 전 팔레트 AAA(7:1 이상), 11~13px 보조·오류 글자는 AA(4.5:1) 이상.
  시안의 원래 값 중 `muted` 는 네 팔레트 모두 3.0:1 안팎이라 **같은 색상에서
  명도만 올려** 4.5 를 넘겼다 (예: log `#6B7480` → `#88909B`).
* `기본`의 다크 오류색도 원래 `#c0392b` 로 3.0:1 이었다 — 같은 색상에서 명도만
  올렸다(`#e08076`, 5.9:1). 라이트는 그대로다.
* **초점 링**을 팔레트마다 강조색으로 그린다(`:focus-visible`). 어두운 바닥에서
  브라우저 기본 링이 사라지는 것은 흔한 사고고, 키보드로만 쓰는 사람에게는
  이것이 커서다.
* `::placeholder` 색도 토큰으로 못 박았다 — UA 기본색은 팔레트를 따라오지 않는다.
* 터미널 팔레트는 `color-scheme: dark` 를 선언한다. 스크롤바와 `select` 목록처럼
  **우리 CSS 가 칠할 수 없는 브라우저 UI** 가 흰색으로 뜨는 것을 막는다.
* 남은 것: `기본`의 선택된 방 블록(파란 바탕 + 흰 글자)은 예전부터 대비가
  낮다(다크 3.2:1). `기본` 은 "지금 모습 그대로"가 요구라 손대지 않고 현재 값을
  테스트로 **고정**만 해 두었다.

## 화면은 모듈로 갈라져 있다

`static/app.js` 는 **진입점 한 장**이고, 화면은 `static/js/` 의 모듈들이 나눠
소유한다. 각 모듈이 **자기 DOM 영역과 자기 상태만** 갖고 남의 노드를 만지지 않는다.

| 모듈 | 소유하는 화면 | 소유하는 상태 |
|---|---|---|
| `roomlist.js` | `#rooms` · 제목 · `#back` · `#room-trouble*` | 방 목록, 현재 방 |
| `addroom.js` | `#add-room` 폼 · `#toggle-add` | 표시 이름 사본 |
| `newrepo.js` | `#new-repo-*` | 만들기 계획 |
| `timeline.js` | `#timeline` · `#messages` · `#older-sentinel` · `#jump-latest` · `#sticky-head` | 대화 모델·가상화·커서·보류 항목·**묶기 판정(머리)** |
| `message-node.js` | 메시지 **한 건**의 DOM (배치별 구조 표 · 묶는가 · 항목 간격) | (없음 — 순수 변환) |
| `composer.js` | `#composer` · `#text` · `#author` · `#reply-chip` | 답장 대상, 표시 이름, 전송 시도 |
| `outbox.js` | `#outbox*` (못 나간 말 띠) | 방 목록 사본, 마지막 아웃박스 상태 |
| `search.js` | `#search-*` | 현재 방 |
| `stream.js` | SSE 연결 · `#refresh` | 연결, 현재 방 |
| `presence.js` | (DOM 없음) 가시성 | 현재 방 |
| `reads.js` | (DOM 없음) 읽음 **모델** | 참가자 커서 지도 · 내 커서 · 구분선 자리 |
| `theme.js` | `#toggle-theme` · `#theme-bar` 와 그 안의 고르는 칸들 | 고른 색 팔레트 · 고른 배치 |
| `update.js` | `#update-bar` 와 그 안의 것들 | 마지막 확인 결과, 갱신 진행 상태 |
| `statusbar.js` | `#status` | 사라지면 안 되는 안내 |
| `bus.js` · `api.js` · `dom.js` | (없음 — 도구) | (없음) |
| `boot.js` | 조립소 | 모듈 핸들, 실패 목록 |

모듈끼리는 **이벤트(`bus.js`)** 로만 이야기한다 (`room:switch` · `rooms:list` ·
`message:new` · `draft:add|settle|fail|retry` · `outbox:state` · `reply:to` ·
`reads:seen|changed|state|ask` · `repo:ready` …).

⭐ 읽음 카운트가 그 경계의 좋은 예다: **모델은 `reads.js` 것**이고(커서 지도 ·
공식), **그리는 것은 `timeline.js` 것**이다(메시지 노드의 주인). 그래서 카운트가
바뀔 때 노드를 다시 만들지 않고 그 자리만 덧입힐 수 있고, 읽음 모듈이 넘어져도
대화는 그대로 뜬다 (카운트만 0 이 된다).
도구(dom·api·status)만 명시적으로 주입한다.

무엇이 좋아지나 — 두 가지가 **구조에서** 나온다:

* **격리.** 한 모듈이 초기화에서 던져도 그 모듈만 실패한다. 예전에는 1000줄짜리
  통짜 IIFE 여서 가상 스크롤 생성자 하나가 터지면 `+` 버튼·방 목록·검색이 전부
  죽었다 — 가상화는 메시지 리스트 하나에만 거는 것인데도. 배선을 앞으로 옮기는
  것은 고장 지점을 뒤로 민 것일 뿐 구조는 그대로였다.
  (실패는 삼키지 않는다: 상태줄·콘솔·`__chat.failures` 에 남는다.)
* **리렌더 국소성.** 메시지 노드를 만드는 곳이 `message-node.js` 하나이고 모델을
  가진 곳이 `timeline.js` 하나다. 그래서 "타임라인을 다시 그리지 않는다"가 전역
  규율로 *감시*할 일이 아니라 소유 관계의 결과가 된다. `rebuiltInView` 카운터는
  남아 있지만 이제 **회귀 감지기**지 규율을 지키는 수단이 아니다.

진입점은 `<script type="module">` 이고 벤더 엔진을 `import` 로 직접 가져온다.
예전에는 인라인 모듈이 `window` 에 엔진을 담아 두고 classic 스크립트가 그것을
집어갔는데, "실렸나 / 그때 실렸나"가 실제 사고 지점이었다. 빌드 단계는 여전히
없다 — 브라우저가 파일을 그대로 받는다.

## 갱신은 한 줄이다

```bash
python -m gitwire_chat update --dry-run    # 무엇을 할지 먼저 본다
python -m gitwire_chat update              # 실제로 갱신한다
```

절차는 이렇다:

1. **바뀔 게 있나 먼저 알린다** — 지금 설치본의 커밋과 원격 최신을 비교한다.
   ⭐ **전송 계층(`gitwire`)도 함께 본다** (아래 참조).
2. **돌고 있는 인스턴스를 찾아 멈춘다.**
3. `pip install --force-reinstall --no-deps "gitwire-chat @ git+…"`
   그리고 밀린 git 의존이 있으면 그것도 한 번 더 (`"gitwire @ git+…"`).
4. **원래 쓰던 포트·옵션으로 다시 띄운다** — 로그인할 때 뜨는 것과 **같은 방식**으로
   (자동 시작과 런처를 공유한다. 아래 「런처는 하나다」).
5. 다시 뜬 것을 확인하고, 무엇이 바뀌었는지 보고한다 (커밋·버전·자원 도장·비교 링크
   · **의존 커밋**).

**바뀔 게 없으면 아무것도 하지 않는다.** 멀쩡한 앱을 재시작시키지 않는다.

### ⭐ `gitwire` 도 함께 갱신한다 (안 하면 조용한 실패다)

`--no-deps` 는 안 바뀐 Flask 를 다시 받지 않기 위한 것이다. 그런데 **git 에서 오는
의존에는 그 논리가 통하지 않는다**: 전송 계층 `gitwire` 는 git URL 로 설치되므로
커밋이 바뀌어도 **버전 문자열이 그대로**(`0.2.0`)다. pip 는 버전으로 판단하니 새
커밋을 가져올 계기가 없고, `--no-deps` 는 아예 쳐다보지도 않는다. 결과는
**"업데이트했는데 그 라이브러리의 수정이 안 내려왔다"** 였다 — 실제로 겪었다
(Windows 콘솔 창 깜빡임 수정이 `gitwire` 쪽이었다).

그래서 `update` 는:

* **의존의 URL 을 코드에 박지 않는다.** `pyproject.toml` 의
  `gitwire @ git+https://…` 가 wheel METADATA(`Requires-Dist`)에 그대로 실리고,
  설치본은 그것을 읽는다. 원천이 하나라 레포를 옮겨도 고칠 곳이 한 곳이다.
* **설치된 커밋은 그 패키지의 `direct_url.json`** 에서 읽는다 (우리 자신과 같은 방법).
* **"최신이다" 판정에 의존을 포함한다.** 앱이 최신이어도 `gitwire` 가 밀렸으면
  갱신이 필요하다고 말한다 (화면도 그렇게 말한다 — 같은 커밋 두 개를 나란히
  보여주며 "새 버전이 있다"고 하지 않는다).
* **밀린 것만 설치한다.** 앱이 최신이면 앱은 건드리지 않고 의존만 갈아치운다.
* **설치 뒤 결과를 다시 읽어 확인한다** — "설치했다"는 우리 주장이 아니라 pip 가
  남긴 기록이 근거다. 원격과 다르면 실패로 보고한다.
* **되돌리기는 두 패키지 모두**를 대상으로 안내한다. 한쪽만 되돌리면 섞인 상태다.

### ⭐ 런처는 하나다 (창이 뜬 진짜 원인)

"이 앱을 백그라운드로 어떻게 띄우나"의 답은 `autostart.py` 에 **한 곳만** 있다
(`background_command` → `start_app`): Windows 는 콘솔 없는 `pythonw.exe`,
macOS·Linux 는 등록된 감독자(launchd·systemd)에게, 감독자가 없으면 직접.
`update` 의 재기동은 그 함수를 **호출만** 한다.

예전에는 `updater.py` 가 자기만의 기동 방식(`DETACHED_PROCESS` + 대장에 적힌
인터프리터)을 갖고 있었다. 그래서 로그인할 때 뜬 앱과 갱신 뒤 뜬 앱이 **다른
방식으로** 떴고, 갱신 버튼을 누르면 **빈 콘솔 창**이 남았다(사용자가 그 창을 닫아
앱이 함께 죽었다). 플래그를 하나 더 붙이는 것은 우회다 — 런처가 둘인 상태를 없애는
것이 수정이다. `tests/test_winspawn.py` 가 두 경로에서 **같은 명령**이 나오는지
단언한다.

### 원래 실행 옵션은 어떻게 아나 — 서버가 자기를 적어 둔다

서버가 뜰 때 자기 자신을 파일 한 장으로 적는다 (`<OS 데이터 디렉토리>/run/<포트>.json`).
포트·`--home`·`--author`·폴 주기·알림 여부가 거기 들어 있고, 갱신은 그것을 읽어
같은 명령으로 다시 띄운다.

* **왜 프로세스를 뒤지지 않나** — `psutil` 같은 의존을 새로 들이거나 OS 별
  `tasklist`·`ps` 를 파싱해야 한다. 이 앱은 셸 전용 도구에 기대지 않는 것을
  규율로 삼고 있다(자동 시작도 같은 이유로 파일 한 장을 쓴다).
* **적는 값은 *해석된* 값이다** — `--home` 을 안 주고 띄웠다면 그 값은
  `GITWIRE_CHAT_HOME` 이나 현재 디렉토리에서 나왔다. 갱신은 **다른 셸에서**
  실행될 수 있어서 그 환경이 같다고 믿을 수 없다. 그래서 해석된 절대 경로를 적는다.
* **살아 있나는 HTTP 로 본다** — `GET /api/version` 의 `pid` 가 적어 둔 것과
  같아야 "그 인스턴스"다(포트를 남이 물려받은 경우를 가른다). ⚠️ Windows 의
  `os.kill(pid, 0)` 은 **프로세스를 종료시킨다** — 생존 확인에 쓸 수 없다.
* 대장을 못 쓰는 환경(읽기전용·권한 없음)이면 경고만 남기고 **채팅은 정상 동작한다.**
  그때 갱신은 인스턴스를 자동으로 못 찾을 뿐이고, 그 사실을 명확히 말한다.

### 앱 프로세스와 분리해서 돈다

서버가 자기 패키지를 갈아치우면서 자기를 재시작하는 구조로 만들지 않았다 —
Windows 에서 파일 락에 걸리고, 실패하면 되돌릴 주체가 사라진다. 갱신은
**별도 프로세스**(이 CLI)가 하고, 앱은 그 CLI 가 멈추고 다시 띄우는 대상이다.

* **먼저 멈춘 다음 갈아치운다.** 순서를 뒤집으면 살아 있는 프로세스가 옛 파이썬
  코드를 메모리에 들고 **새 정적 파일**을 서빙하는 섞인 상태가 된다.
* ⚠️ **Windows 에서 `gitwire-chat update` 로 부르면** 지금 돌고 있는 프로세스가
  `Scripts\gitwire-chat.exe` 그 파일이라 pip 가 그것을 지우지 못한다. 그래서
  자동으로 `python -m gitwire_chat update` 로 갈아타고 그 사실을 알린다.
* 프로세스 종료는 `os.kill` 이고, 재기동은 **자동 시작과 같은 단일 원천**
  (`autostart.start_app`)이 한다 — `pkill`·`taskkill` 같은 도구에 기대지 않는다.
  파이썬 하나로 세 OS 를 덮는다.

### 깨진 갱신이 스스로를 못 고치는 상태로 끝내지 않는다

* **설치가 실패하면** 멈춘 인스턴스를 **옛 버전으로 되살리고**(코드는 아직 안
  바뀌었다) pip 가 뭐라고 했는지 그대로 보여준다.
* 되돌리기가 가리키는 곳은 `--url` 로 바꾼 주소가 아니라 **설치본이 실제로 온 곳**
  이다 — 그 커밋은 거기에만 있다. (두 좌표를 구분해서 들고 간다.)
* **갱신 후 앱이 뜨지 않으면** 실패로 보고하고 ① **이번 시도의** 재기동 로그 꼬리와
  ② **직전 커밋에 못 박은 되돌리기 명령**을 출력한다:

  ```bash
  pip install --force-reinstall --no-deps "gitwire-chat @ git+…@<직전 커밋>"
  # 이번에 gitwire 도 갈아치웠다면 그것까지 함께 (한쪽만 되돌리면 섞인 상태다)
  pip install --force-reinstall --no-deps "gitwire @ git+…@<직전 커밋>"
  ```

  조용히 "죽은 채로 종료"하지 않는다. 직전 커밋은 설치 **전에** 읽어 둔다.
  (로그는 이어 쓰지만 재기동마다 경계선을 남긴다 — 지난 재기동의 *정상* 출력이
  꼬리를 채워서 "잘 떴는데?" 하고 엉뚱한 줄을 읽게 되는 일을 막는다. 실측에서
  꼬리 25줄의 절반이 지난 두 번의 정상 출력이었다.)

### 대장에 없는 인스턴스가 돌고 있으면 중단한다

이 기능이 없던 버전으로 떠 있는 앱은 pid 도 실행 옵션도 알 수 없다 — 멈출 수도,
원래 옵션으로 다시 띄울 수도 없다. 그 상태에서 갈아치우면 섞인 상태가 되므로
**중단하고** 무엇을 하면 되는지 말한다(Ctrl+C 로 끄고 다시 실행 → 그다음부터는
자동으로 된다). 정말 무시하려면 `--ignore-unmanaged`.

다른 venv 에서 도는 앱은 세지 않는다 — `/api/version` 의 `prefix` 가 다르면
우리가 건드릴 파일과 무관하다. `prefix` 를 안 알려주는 옛 버전은 보수적으로 막되
**사유를 구분해서** 말한다: "같은 설치본이다"(확인됨)와 "같은 곳인지 알 수 없다"는
다른 문장이다 — 모르는 것을 안다고 말하면 그 보고가 거짓이 된다.

그리고 옛 버전은 `/api/version` 자체가 없어서 404 를 준다. 그것을 "아무것도 없다"로
보면 **처음 한 번**이 조용히 깨지므로, 옛 버전에도 있던 `/api/settings` 로 한 번 더
물어본다.

### 자동 시작(`autostart`)이 등록돼 있으면 감독자에게 맡긴다

macOS(launchd `KeepAlive`)·Linux(systemd)는 **죽은 프로세스를 되살린다.** 거기서
프로세스를 직접 죽이면 감독자가 옛 코드로 다시 띄우거나(macOS 는 `ThrottleInterval`
뒤에) 유닛 상태가 어긋난다 — 경합이다.

그래서 등록된 포트와 같은 포트의 인스턴스는 멈춤·재기동을 **감독자에게 맡긴다**:

| OS | 멈춤 | 재기동 | 되살리나 |
|---|---|---|---|
| Windows | `os.kill` (시작 폴더는 감독자가 아니다) | `Popen` 으로 분리 실행 | 아니오 |
| macOS | `launchctl bootout` | `launchctl bootstrap` | **예** |
| Linux | `systemctl --user stop` | `systemctl --user start` | **예** |

`enable`·등록 파일은 건드리지 않는다 — 자동 시작 등록은 그대로 남는다. 그리고
이 경로는 옵션 보존을 공짜로 얻는다(등록 파일에 박혀 있는 값이 그대로 쓰인다).
감독자에게 맡기지 못하면 직접 종료하되 **그 사실과 되살릴 수 있다는 경고를 남긴다.**

### 옵션

| 옵션 | 뜻 |
|---|---|
| `--dry-run` | 무엇을 멈추고 무엇을 설치하고 어떻게 다시 띄울지만 보여준다 |
| `--url` | 설치할 git 주소 (기본: 지금 설치본이 온 곳). 조회와 설치가 같은 주소를 본다 |
| `--port` | 그 포트의 인스턴스만 |
| `--force` | 최신이어도 다시 설치 (설치본이 깨졌을 때) |
| `--no-restart` | 멈추고 설치까지만 |
| `--ignore-unmanaged` | 대장에 없는 인스턴스를 무시하고 진행 |
| `--dir` | 인스턴스 대장 디렉토리 (테스트·격리) |

### 앱 안에서 버튼 하나로 갱신까지 간다

사이드바 맨 아래에 「업데이트 확인」이 있다. 흐름은 이렇다:

1. **확인** — 원격을 한 번 본다(`POST /api/update/check`). 새 것이 있으면
   `설치본 → 원격` 커밋과 「무엇이 바뀌었나」 비교 링크를 보여준다.
2. **「지금 갱신」** — 아직 아무것도 하지 않는다. 무엇이 바뀌는지 다시 보여주고
   「갱신한다」/「취소」를 묻는다.
3. **「갱신한다」** — `POST /api/update/run`. 서버는 **정본 CLI 를 분리된
   프로세스로 띄우고 즉시 202 로 답한다.**
4. **서버가 죽는다.** 화면은 그 구간을 *기다리는 상태*로 버틴다.
5. **새 서버가 뜨면 알아서 새 화면으로 간다.** 자원 도장이 바뀌었으므로 다시
   불러오는 것만으로 새 JS·CSS 가 내려온다.

칠 명령과 복사 버튼은 그대로 남아 있다 — **CLI 가 여전히 정본**이다.

#### 버튼은 갱신하지 않는다 — CLI 를 띄운다

`POST /api/update/run` 이 하는 일은 `python -m gitwire_chat update` 를 분리된
프로세스로 띄우고 돌아오는 것뿐이다. 멈춤·설치·재기동·**실패 시 되돌리기와
안내**는 그 CLI 가 이미 한다(위 절들). 서버가 자기 패키지를 갈아치우며 자기를
재시작하는 구조로 만들지 않는다 — Windows 파일 락에 걸리고, 실패하면 되돌릴
주체가 사라진다. 그리고 앱이 아예 안 뜨는 상태에서는 버튼이 없다.

`--force`·`--url` 처럼 위험을 늘리는 스위치는 HTTP 로 열지 않았다. 화면은
"최신으로 올린다" 하나만 한다.

#### 왜 예전 판단을 뒤집었나 — 드라이브바이는 막힌다

한때 이 자리에는 실행 엔드포인트가 **없었다.** 근거는 이랬다 — "루프백 ·
인증 없음 설계에서 '누르면 앱을 죽이고 갈아치우는' 엔드포인트는 아무 웹페이지의
폼 전송 하나로 트리거되고 막을 수단이 없다."

**앞부분은 맞고 뒷부분이 틀렸다.** 로그인 없이도 "우리 화면에서 온 요청"만
받는 것은 표준 수단으로 된다. 세 겹이고 각각 다른 것을 막는다
(`gitwire_chat/csrf.py`):

| 겹 | 무엇을 막나 |
|---|---|
| **커스텀 요청 헤더** `X-Gitwire-Chat: update` | 평범한 HTML `<form>` 은 요청 헤더를 붙일 수 없다 → 드라이브바이의 주된 형태가 여기서 죽는다. 스크립트로 붙이면 단순 요청이 아니게 되어 브라우저가 **preflight** 를 먼저 보내고, 우리는 CORS 를 켜지 않으므로 **본 요청이 나가지도 못한다** |
| **`Sec-Fetch-Site`** | 브라우저가 붙이는 값이라 페이지 JS 가 위조할 수 없다(금지된 헤더 이름). `same-origin` 이 아니면 거절 |
| **`Origin`** | 있으면 `Host` 자신과 같아야 한다. `127.0.0.1:8770` 로 열었든 `localhost:8770` 으로 열었든 자기 자신이면 통과, `null`(샌드박스 iframe)은 거절 |

⚠️ **`Sec-Fetch-*` 가 없으면 통과시킨다.** 그 헤더를 안 보내는 오래된
브라우저·`curl`·스크립트에서도 우리 UI 는 동작해야 한다 — *방어가 정상 사용을
막으면 그것도 실패다.* 그 경우에도 커스텀 헤더 요구는 그대로 성립한다.

**1회용 토큰은 두지 않았다.** 이 문이 막는 상대는 *다른 오리진의 페이지*이고
그건 위 세 겹으로 막힌다. 같은 기기에서 도는 프로그램은 `GET /`(인증 없음)로
토큰을 그냥 읽어 갈 수 있어서 이득이 없고, 서버가 재기동되면 옛 토큰이 죽어서
**정상 경로만** 깨진다.

#### ⚠️ 그래서 루프백 전용이 더 중요해졌다 — 절대 외부에 노출하지 마라

이 문은 **"브라우저를 거친 다른 오리진"** 을 막는다. 막지 **못하는** 것은
*이 기계에 이미 코드를 실행할 수 있는 상대*다 — 헤더 세 개는 아무 HTTP
클라이언트가 마음대로 붙일 수 있고, 우리는 그것을 구분할 수단이 없다(인증이
없다). 즉 **이 포트에 도달할 수 있는 것 = 이 앱을 재설치시킬 수 있는 것**이다.

전에는 그 결과가 "내 채팅 기록을 읽는다"였고, 이제는 **"내 컴퓨터에서
`pip install` 을 돌리게 한다"** 다. 위험의 종류가 올라갔다.

앱은 `127.0.0.1` 에만 바인드하고 그것을 바꾸는 옵션이 없다(`__main__.py` 도크).
포트 포워딩·리버스 프록시·`ssh -R`·컨테이너 포트 공개로 이 포트를 밖으로
내보내지 마라. 꼭 원격에서 써야 한다면 **앞단이 인증과 함께** 책임져야 한다
(SSH 터널 안에서 쓰거나, 인증 붙은 프록시 뒤에 두고 그 프록시가 이 경로를
차단하는 식으로).

#### 안 돌아오면 · 두 번 누르면 · 바뀔 게 없으면

* **안 돌아오면** — 화면은 `GET /api/version` 을 1초마다 물어보고 **pid** 로
  가른다(그대로 = 아직 옛 서버, 실패 = 멈춤, 달라짐 = 새 서버). 240번 물어보고도
  답이 없으면 **포기하고** 칠 CLI 명령과 갱신 기록 파일 위치를 보여준다.
  무한 대기는 하지 않는다.
* **동시 실행** — 연타·갱신 중 재누름은 화면이 막고, 다른 탭·다른 인스턴스는
  서버가 409 로 거절한다. 같은 서버 안에서는 자식 프로세스에게 물어보므로
  확정이고, 다른 프로세스는 대장 디렉토리의 자물쇠 파일(`O_CREAT|O_EXCL`)로
  갈린다. ⚠️ 그 자물쇠를 **풀어 줄 주체가 갱신에 죽으므로**, 남의 자물쇠는
  "갱신 기록이 90초 동안 조용하면 끝난 것"으로 **추측**한다 — 한계와 그것이
  어느 방향으로 틀리는지는 `gitwire_chat/updaterun.py` 모듈 도크에 적어 뒀다.
* **바뀔 게 없으면** 아무것도 띄우지 않고 그렇게 답한다(HTTP 200,
  `started: false`). 이 판정은 **서버가** `ls-remote` 로 한다 — 화면의 말을
  믿지 않는다.
* **이 인스턴스가 대장에 없으면 거절한다.** 그 상태로 갱신하면 CLI 가 이 앱을
  찾지 못해 멈추지도 다시 띄우지도 못하고 파일만 갈아치운다 = 살아 있는 앱이
  **옛 파이썬 코드로 새 정적 파일을 서빙하는 섞인 상태**. 조용한 고장이라 아예
  막고 CLI 를 안내한다.
* **확인 시점 = 누를 때만.** 확인은 `git ls-remote` 한 번 = 실제 네트워크
  왕복이다. 폴링으로 돌리면 로컬 앱이 사용자가 모르는 사이에 외부 호스트로
  나가는 동작이 하나 생긴다 — 이 앱의 다른 어떤 것도 그렇게 하지 않는다(방
  폴링은 사용자가 등록한 레포만 본다). 누르기 전에는 이 모듈이 네트워크를 전혀
  쓰지 않는다.

### 무엇으로 확인하나

* `tests/test_updater.py` — 대장 왕복·출처 판정(git/editable/불명)·`ls-remote`
  (진짜 로컬 레포로)·세 포맷의 `--port` 읽기·감독자 판정, 그리고 **흐름 전부**:
  바뀔 게 없으면 아무것도 안 하는가 · dry-run · 대장 밖 인스턴스 중단 ·
  설치 실패 시 되살리기 + 되돌리기 명령 · 다시 안 뜰 때 로그 꼬리.
* 같은 파일의 **실제 프로세스 왕복** — 앱을 진짜로 띄우고, 대장에 스스로 적는지
  확인하고, `stop_instance` 로 멈추고, 적혀 있던 명령으로 다시 띄워 같은 앱이
  뜨는지 본다. 중간의 pip 만 빠져 있다.
* pip 를 포함한 전체 왕복은 별도 venv 에 **옛 커밋을 설치해 두고** 손으로
  실증한다 (사용자 인스턴스가 아니라 그 venv 로). UI 경로도 같은 방법으로
  실증했다 — 로컬 bare 레포를 원격으로 삼아 옛 커밋을 설치하고, 빈 포트에
  띄우고, `POST /api/update/run` 을 보내 **버전 0.2.0 → 0.2.1 · 자원 도장 변경 ·
  pid 변경 · `/api/rooms` 200** 까지 확인했다.
* `tests/js/render.test.mjs` — 켤 때 원격을 안 보나 · 누르면 명령을 보여주나 ·
  「지금 갱신」이 확인을 받기 전에는 안 나가나 · 실행 요청에 화면 표식 헤더가
  붙나 · **서버를 잃는 구간을 버티나**(옛 서버 → 요청 실패 → 새 pid → 새 화면) ·
  안 돌아올 때 포기하고 안내하나 · 연타가 한 번만 나가나 · 실패 사유와 서버
  힌트가 화면에 드러나나 · 이 모듈이 죽어도 나머지가 사나.
* `tests/test_updater.py` 「화면에서 온 요청인가」 — 헤더 없는 POST · 폼 전송
  모양 · 다른 `Origin` · `Sec-Fetch-Site: cross-site`/`same-site` · `Origin: null` ·
  값만 다른 헤더가 **전부 거절되는지**, 그리고 `Sec-Fetch-*` 를 **안 보내는
  클라이언트가 통과하는지**. 실행기 쪽은 자물쇠·동시 실행·대장 밖 거절 ·
  **진짜 프로세스로 CLI 를 띄우고 기록을 남기고 자물쇠를 푸는지**(`--dry-run`
  으로 띄우므로 아무것도 멈추거나 설치하지 않는다).
* ⭐ `tests/test_browser_smoke.py` — **진짜 브라우저로 드라이브바이를 두들긴다.**
  다른 오리진(`localhost:B`)의 페이지가 숨은 폼 자동 전송 · 커스텀 헤더 fetch ·
  헤더 없는 단순 요청 · `no-cors` 넷으로 공격하고, 같은 오리진 페이지가 정상
  경로와 **헤더만 뺀** 경로를 보낸다. 판정: 크로스 오리진 POST 는 전부 403 ·
  커스텀 헤더 요청은 preflight 에서 죽어 **POST 자체가 도달하지 못한다** ·
  갱신은 **정상 경로 하나에서만** 시작된다. (논리로 "폼은 헤더를 못 붙인다"고
  적어 두는 것과, 브라우저가 실제로 그러는지 보는 것은 다른 일이다.)

## 갱신하면 화면도 같이 갱신된다 (정적 자원 도장)

갱신은 파이썬 패키지만 갈아치운다. 브라우저는 그걸 모른다. `/static/app.js` 라는
URL 이 그대로면 캐시에 있던 **옛 JS·CSS** 를 계속 쓴다 — 그게
**"업데이트했는데 화면은 그대로"** 다. 실제로 이 앱은 갱신마다 사람에게
"Ctrl+Shift+R 반드시 하세요"를 안내해야 했고, 갱신이 명령 한 줄로 짧아지면
그 함정은 **더 자주** 터진다(새로고침을 잊기 쉬워지므로).

그래서 자원 URL 에 **내용 도장**을 박는다:

```
/assets/3c098c63750d/app.js
/assets/3c098c63750d/js/boot.js
/assets/3c098c63750d/vendor/tanstack-virtual-core/index.js
/assets/3c098c63750d/style.css
```

### 도장은 내용 해시다 — 버전 문자열이 아니다

후보였던 `importlib.metadata.version()` 은 **이 프로젝트에서 동작하지 않는다.**
배포가 git 커밋으로 나가고 버전 문자열은 `0.2.0` 에 머물러 있어서, 같은 버전으로
열 번을 배포해도 값이 안 바뀐다 — 캐시가 또 안 깨진다. `git describe` 류는 아예
못 쓴다(설치본에 체크아웃이 없다).

도장은 정적 트리 **모든 파일의 내용**을 sha256 으로 접은 값이다. 성질이 정확히
필요한 그대로다:

| 상황 | 도장 |
|---|---|
| 같은 버전 문자열로 재배포 · 파일이 바뀜 | **바뀐다** ⭐ |
| 재설치했지만 파일 내용은 그대로 (mtime 만 다름) | 그대로 |
| 벤더 파일·CSS 만 바뀜 | 바뀐다 |
| 파일이 늘거나 이름이 바뀜 | 바뀐다 |

### 왜 경로에 박나 (`?v=` 가 아니라)

프런트엔드가 **ES 모듈 그래프**다. `app.js` 가 `./js/boot.js` 를 부르고 그것이
다시 14개를 부른다. `app.js?v=…` 처럼 질의만 붙이면 **그 한 파일만** 새로 받고
하위 모듈은 옛 캐시에서 나온다 — 하나라도 옛 파일이 섞이면 "그대로" 보다
**더 이상한 증상**이 난다.

경로에 박으면 그 문제가 정의상 사라진다. 상대 import 가 같은 접두사 안에서
해석되므로 도장 하나가 **그래프 전체**(벤더 포함)를 한꺼번에 갈아 준다.
빌드 단계도, 내용 재작성도, import 맵도 없다.

### 셸 HTML 은 캐시하지 않는다

새 URL 이 그 HTML 안에 들어 있으니, 셸이 캐시되면 위의 전부가 무력화된다.
그래서 `/` 는 `Cache-Control: no-store` 로 준다. 첫 페인트 전에 도는 인라인
테마 조각도 셸 안에 있어서 같이 신선해진다. 도장이 맞는 자원은 반대로
`max-age=31536000, immutable` 로 준다 — 내용이 바뀌면 URL 이 바뀌니까.

옛 도장으로 들어온 요청(갱신 직후까지 열려 있던 탭)은 **지금 파일**을 주되
`no-store` 로 주고 서버 로그에 경고를 남긴다. 옛 파일을 보관하지 않으므로 줄 것이
그것뿐인데, 그걸 `immutable` 로 못 박으면 틀린 내용이 옛 URL 에 영구히 굳는다.

### 무엇으로 확인하나

* `tests/test_assets.py` — 바꾸면 바뀌고 안 바꾸면 그대로인가, 같은 버전
  재배포에도 바뀌는가, 셸이 도장 없는 URL 을 뱉지 않는가, 헤더가 맞는가.
* `tests/test_browser_smoke.py` 의 「같은 버전으로 재배포해도 브라우저가 새
  파일을 받는다」 — **진짜 브라우저**로 같은 프로필(=캐시 살아 있음)로 세 번
  연다. 1회 옛 파일 → 2회 파일만 고친 뒤 새 코드가 **실행되는지** → 3회
  안 고쳤을 때 진입점을 **다시 안 받는지**(캐시 명중). 3회가 반대 방향을 닫는다.

## 개발

```bash
pip install -e .            # 앱 (gitwire 는 GitHub 에서 받아온다)
pip install -e ../gitwire   # 기반도 함께 고칠 때만 — 로컬 체크아웃으로 갈아끼운다
python -m pytest -q
```

두 번째 줄이 앞서 설치된 `gitwire` 를 로컬 체크아웃으로 덮어쓴다. 기반 API 를
바꾸면서 소비자를 함께 고칠 때 이 형태로 쓴다. 되돌리려면
`pip install --force-reinstall "gitwire @ git+https://github.com/yunhyuk-choi/gitwire.git"`.

핵심 검증은 **앱 인스턴스 두 개가 로컬 bare 레포를 방으로 삼아 실제 git 으로
대화하는 것**이다(`tests/test_two_instances.py`). 대역이 아니라 진짜 git 이다 —
clone·push·커서 영속은 흉내내면 아무것도 증명하지 못한다. 나머지 테스트는
gitwire 채널을 주입 가능한 대역으로 갈아끼워 네트워크 없이 돈다.

### 프런트엔드는 세 층으로 검증한다

한 층으로는 부족하다는 것을 **비싸게 배웠다.** stub DOM 테스트가 22/22 로 통과하는
동안 앱은 브라우저에서 완전히 죽어 있었다(모든 버튼 무반응). 그래서 층을 나눈다 —
서로를 대체하지 않는다.

| 층 | 무엇을 본다 | 못 보는 것 |
|---|---|---|
| `node --check` + stub DOM (`tests/js/`, `tests/test_frontend.py`) | `createApp()` 을 **그대로 import 해** stub 런타임(document·fetch·EventSource)을 주입하고 구동한다 — 프로덕션 진입점이 하는 일과 같은 모양이라 하네스와 실물이 어긋나지 않는다. **DOM 조작 횟수와 노드 동일성**을 센다 — "리렌더가 없다"를 주장이 아니라 수로 확인한다. 가상 스크롤 엔진은 대역이 아니라 **벤더링된 진짜**를 구동한다 | Node 안에서 돈다(브라우저에만 없는 전역), 로딩 순서를 건너뛴다, `index.html` 을 안 읽는다 |
| 벤더 원문 검사 (`tests/test_vendor_assets.py`) | 브라우저로 가는 JS 에 **Node 전용 전역**(`process` · `require()` · `module.exports` · `__dirname` …)이 하나도 없다. 출처·LICENSE·버전 표기도 본다 | 실행하지 않는다 — 문법·동작은 안 본다 |
| **브라우저 연기 테스트** (`tests/test_browser_smoke.py`) | 진짜 헤드리스 브라우저로 페이지를 연다. **콘솔에 `Uncaught` 가 하나라도 있으면 실패**, 그리고 브라우저가 **`/api/rooms` 를 실제로 불렀나**(= 배선까지 갔나) | 느리다. 세밀한 카운팅은 못 한다 |

브라우저 연기 테스트가 상태코드를 근거로 쓰지 않는 이유: 앱이 완전히 죽어 있던
그때도 페이지 응답은 **200 이었다.** 200 은 아무것도 증명하지 않는다.

색 테마도 같은 규율로 본다 — **팔레트마다** 실제로 앱을 열어 콘솔 `Uncaught` 0 ·
`/api/rooms` 호출 · 루트에 팔레트가 찍혔는지를 확인하고, 진짜 `style.css` 를 물린
페이지에서 `getComputedStyle` 값을 회수해 팔레트 정의와 **하나씩 대조**한다
("적용했다"는 클레임이 아니라 브라우저가 계산한 값이 근거다). 테마를 심는 씨앗
페이지는 **테스트 안에만** 있다 — 앱에 `?theme=` 같은 뒷문을 뚫지 않았다.

크로미움 계열 브라우저(Edge·Chrome·Chromium)를 PATH 와 각 OS 의 관례적 설치
위치에서 찾는다. **없으면 SKIP** 한다 — 리눅스 CI·맥에서 스위트가 깨지지 않는다.
SKIP 사유는 `-ra`(기본 `addopts`)로 매 실행 요약에 뜬다. 경로를 직접 주려면
`GITWIRE_CHAT_BROWSER=/path/to/msedge`.

손으로 같은 것을 보고 싶으면 (앱이 `<포트>` 에 떠 있을 때):

```bash
EDGE="/c/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"
"$EDGE" --headless=new --disable-gpu --no-sandbox --user-data-dir=/tmp/edge-smoke   --enable-logging=stderr --log-level=0 --virtual-time-budget=8000   --dump-dom "http://127.0.0.1:<포트>/" > dom.html 2> console.txt
grep -iE 'CONSOLE|Uncaught' console.txt      # 여기에 Uncaught 가 있으면 앱은 죽은 것이다
```

### 가상 스크롤 엔진을 올릴 때

`static/vendor/tanstack-virtual-core/` 에 npm 배포본의 `dist/esm/*` 와 `LICENSE` 를
복사한다(빌드 단계 없음). ⚠️ **그대로 복사하면 안 된다** — 상류는 번들러가 있다는
전제로 `NODE_ENV` 환경변수 참조를 남겨 두고, 브라우저에는 그 전역이 없다. 절차와
경위는 `static/vendor/tanstack-virtual-core/VENDORING.md` 에 있고,
`tests/test_vendor_assets.py` 가 빠뜨림을 잡는다.

파일은 UTF-8(BOM 없음)·LF 로 쓴다. 코드·주석·UI 문구는 한국어다.

라이선스는 MIT (`LICENSE`).

## 보안 모델 · 설계상 그런 것

한계처럼 보이지만 **의도한 설계**인 것들이다. 쓰기 전에 알고 있어야 한다.

* **루프백에만 바인드한다 — 그래서 인증이 없다.** `127.0.0.1:8770` 에서만 뜨고
  바꿀 수 있는 옵션이 없다. 내 컴퓨터에서 나만 쓰는 앱이라는 전제 위에서
  로그인·세션을 생략했다. 밖에서 접근해야 한다면 그건 이 앱이 아니라
  앞단(SSH 터널·인증 붙은 리버스 프록시)이 책임질 일이다.
* ⚠️ **그 전제가 「갱신」 버튼으로 더 무거워졌다.** `POST /api/update/run` 은
  이 앱을 멈추고 `pip install` 을 돌리고 다시 띄운다. 브라우저를 거친 다른
  오리진은 세 겹으로 막지만(커스텀 요청 헤더 + `Sec-Fetch-Site` + `Origin` —
  「갱신은 한 줄이다」 절), **이 기계에서 이미 코드를 실행할 수 있는 상대는
  막지 못한다.** 헤더는 아무 HTTP 클라이언트가 붙일 수 있고 우리는 그것을
  구분할 수단이 없다. 즉 **이 포트에 도달할 수 있는 것 = 이 앱을 재설치시킬
  수 있는 것**이다. 이 포트를 절대 외부로 내보내지 마라(포트 포워딩·리버스
  프록시·`ssh -R`·컨테이너 포트 공개). 그게 싫으면 갱신은 CLI 로만 하면 된다 —
  버튼은 편의이고 CLI 가 정본이다.
* **레포 접근권이 곧 참여권이다.** 방 = git 레포이므로 그 레포에 접근할 수 있는
  사람이 참가자다. per-message ACL 은 없고, 나중에 초대한 사람도 과거 대화를
  전부 본다 — 팀 채팅에서 흔한 동작이며, git 히스토리를 그대로 쓰는 이 구조의
  자연스러운 귀결이다.
* **대화가 쌓이면 레포도 커진다.** 메시지 한 건 = 파일 한 건 = 커밋이다. 채팅
  기록이 로컬에 쌓이는 것 자체는 채팅 앱의 정상 동작이고, 정말 줄이고 싶으면
  `gitwire compact`(파괴적) 또는 shallow clone 이 있다.
* **검색은 레코드를 읽어서 찾는다.** 인덱스를 두지 않았다. 파일 안을 찾는 일이
  원래 그렇고, 방 하나가 사람이 쓰는 대화인 한 이 방식으로 충분하다.
* **레포 생성은 사람이 누를 때만 한다.** 토큰이 있어도 조용히 만들지 않는다 —
  무엇이 만들어지는지(소유자·이름·공개범위) 보여주고, 누른 뒤에만 만든다.

## 정직한 한계

이 앱이 **못 하는 것**들이다. 쓰기 전에 반드시 읽어라.

* **실시간이 아니다.** 지연 = 폴 주기다. 기본 15초면 상대가 보낸 말이 최악
  15초 + pull 시간 뒤에 뜬다. 주기를 줄이면 그만큼 호스트에 요청이 늘어난다
  (rate limit 주의). 내가 보낸 말은 낙관적 업데이트로 즉시 보이지만, 그건
  화면일 뿐 상대에게 도착한 시점과는 다르다.
* **타임라인 조회는 원격을 보지 않는다 — 그래서 "마지막 폴 시점" 기준이다.**
  대화 기록은 이미 로컬 클론에 있고, 신선도는 폴러가 맡는다. 방을 여는 순간에는
  **화면을 막지 않고** 백그라운드로 한 번 더 당기며(새 것은 SSE 로 뒤따라 붙는다),
  「지금 당겨오기」 버튼은 언제나 즉시 원격을 본다. 이 설계 이전에는 조회 한 번이
  `git ls-remote` 왕복(실측 1.3초)을 매번 물고 있어서 **최근 50건 조회가
  1.4~2.9초** 였다. 실측 before/after (진짜 GitHub 원격, 5회 중앙값):
  최신 쪽 **1463ms → 51ms**, 위로 페이징 **1359ms → 49ms**.
* **타임라인 조회는 *커밋된* 레코드를 읽는다.** 보내기는 파일을 디스크에 쓰고
  즉시 돌아오고, 커밋은 아웃박스가 곧바로(수십 ms 안에) 한다. 그 아주 짧은 사이에
  **페이지를 통째로 새로고침하면** 방금 보낸 한 줄이 잠깐 빠져 보일 수 있다
  (화면에 떠 있는 낙관적 말풍선은 영향받지 않는다). 커밋되면 그대로 보인다 —
  잃는 것은 없다.
* **진짜 push 알림이 없다.** 서버가 우리를 깨우지 않는다. 전부 폴링이라
  OS 알림도 폴 주기만큼 늦게 뜬다.
* **읽음 표시의 지연은 구조적이다.** 상대가 읽음 → 상대의 push → 내 폴링이라,
  메시지의 "안 읽은 수"가 **폴 주기(기본 15초)만큼, 실질적으로 30초쯤** 늦게
  줄어든다. 우회로가 없다 — 상대가 우리를 깨울 방법이 없기 때문이다. 내가 읽는
  쪽(방 목록 뱃지)은 로컬이라 즉시 줄어든다.
* **읽음 카운트의 분모는 "커서 파일을 올린 사람"이다.** 앱을 설치했지만 켜지
  않는 사람은 커서가 움직이지 않아 카운트가 영구히 ≥1 로 남는다. 그게 사실이라
  특별 처리하지 않는다 (조용히 "다 읽음"이 되는 것보다 낫다). 반대로, 방을
  한 번도 열지 않은 사람은 분모에 아예 들어오지 않는다.
* **읽음 커서는 마지막 값만 남는다.** "언제 읽었나"의 이력이 아니다 —
  `participants/` 는 덮어쓰는 경로다 (gitwire README 「참가자별 가변 상태」).
* **내 다른 기기에서 보낸 말은 이 기기의 뱃지에 잠깐 세어질 수 있다.** 읽은
  위치(①)는 기기별 로컬 커서이기 때문이다. 그 방을 열면 곧 0 이 된다.
* **메시지 삭제가 사실상 안 된다.** append-only 다. 지우려면 히스토리 재작성
  (`gitwire compact`)이 필요하고 그건 모든 참가자에게 파괴적이다.
* **참가자 사이의 순서는 시계 보정 오차만큼 흔들린다.** 타임스탬프 자체는
  **밀리초** 해상도이고(`20260903T041210032Z`), 한 사람이 보낸 메시지들은 그
  해상도로 순서대로다(같은 밀리초에 두 건을 내거나 그 사이 시계가 뒤로 조정되면
  아래의 ID 규칙으로 갈린다). 뒤집힐 수 있는 것은 **서로 다른 참가자의 메시지가
  거의 동시에 발행됐을 때**뿐이다 — 공통 시계(git 호스트 `Date` 헤더 기준)의
  잔여 오차가 대략 ±(0.5 + RTT/2)초라서, 그 안에서 앞뒤가 바뀔 수 있다.
  타임스탬프가 같으면 메시지 ID 로 갈리는데, 그 순서는 **모든 참가자에게 동일**
  하다(ID 사전식 정렬 = 표시 순서). 즉 화면이 사람마다 달라지지는 않는다.
* **여러 명이 초 단위로 쏟아붓는 용도가 아니다.** 동시 발행이 잦으면 push 경합
  재시도가 늘어난다. 정확성은 유지되지만 느려진다.
* **방에 처음 합류할 때 과거를 전부 내려받는다.** 화면에 그리는 것과 서버에서
  읽는 것은 이미 "본 만큼"이지만(가상 스크롤 + keyset 페이징), *클론*은 여전히
  전량이다. 부분 클론(`--filter=blob:none`)으로 줄여 보려다 측정에서 손해로
  나와 넣지 않았다 — 근거는 gitwire README 「부분 클론을 쓰지 않는 이유」.
* **「내 것」은 사람이 아니라 설치본 단위다.** 같은 사람이 다른 컴퓨터(다른
  `home`)에서 보낸 말은 여기서 '남의 것'으로 보인다 — 봉투 `sender` 는 참가자
  *프로세스* 식별자이기 때문이다. 설치본 식별자를 잃어버리고 새로 만들어진
  경우(홈 디렉토리를 지웠다)도 마찬가지로, 그 이전에 쓴 말은 왼쪽에 남는다.
  **여러 신원을 '나이기도 하다'로 묶는 설정을 두지 않았다.** 이유는 두 가지다:
  (1) 봉투에 서명이 없어서 "이 옛 신원이 나였다"는 주장을 앱이 **검증할 수
  없다** — 사람이 적어 준 값을 그대로 믿는 수밖에 없다. (2) 예전 기본 sender
  는 `<유저>.<호스트>` 였는데 이건 **전역 유일하지 않다**. 그런 값을 별칭으로
  받아들이면 같은 유저명·호스트명을 쓰는 **남의 메시지까지 내 것이 된다** —
  고치려던 것보다 나쁜 고장이다. 과거 레코드를 고쳐서 맞추는 길은 아예 없다
  (append-only 이고 히스토리 재작성은 모든 참가자에게 파괴적이다).
* **아주 오래된 대화로 계속 거슬러 올라가면 모델이 커진다.** DOM 노드 수는
  상수로 유지되지만(가상 스크롤), 불러온 메시지 자체는 메모리에 쌓인다.
  방을 바꾸거나 새로고침하면 비워진다.
* **한 모듈이 죽으면 그 영역은 정말로 안 된다.** 격리는 "나머지가 산다"는
  뜻이지 "고장이 사라진다"는 뜻이 아니다. 타임라인이 서지 못하면 대화는 보이지
  않고 그 자리에 결함이 뜬다 — 느린 대체 경로로 감추지 않는다(그게 의도다).
* **브라우저 검증은 연기 감지기지 E2E 가 아니다.** 크로미움 계열 한 종류를
  헤드리스로 열어 **처리되지 않은 예외**와 **첫 배선**(`/api/rooms` 호출)만 본다.
  사람이 클릭·입력하는 흐름 전체, 그리고 Firefox·Safari 는 자동 검증 범위 밖이다.
  이 정도로도 "앱이 통째로 죽었는데 테스트는 전부 통과"는 다시 일어나지 않는다.

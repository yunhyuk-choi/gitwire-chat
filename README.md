# gitwire-chat

**중앙 서버 없이 git 레포를 메시지 저장소로 쓰는 로컬-퍼스트 비동기 채팅.**

각 참가자가 자기 컴퓨터에서 이 앱을 띄우고, 공유 private git 레포 하나를 통해
대화한다. 서버 운영이 0이고, 네트워크는 egress(`pull`/`push`)만 쓴다.

```
   내 브라우저 ──HTTP/SSE──▶ 내 로컬 앱 ──push──▶ ┌──────────────┐ ◀──push── 상대 앱
   (localhost)                          ◀──pull── │ private repo │ ──pull──▶
                                                  └──────────────┘
```

전송 계층은 **[gitwire](https://github.com/yunhyuk-choi/gitwire)** 가 전부 담당한다. 이 앱에는 git 명령이
한 줄도 없다. gitwire 는 레코드 `payload` 안을 해석하지 않으므로, "메시지"라는
개념은 오직 여기서 정의된다.

---

## 띄우기

```bash
git clone https://github.com/yunhyuk-choi/gitwire-chat.git
cd gitwire-chat
pip install .          # 전송 계층(gitwire)은 의존성으로 함께 받아온다

python -m gitwire_chat
# → http://127.0.0.1:8770
```

레포 하나만 클론하면 된다 — [gitwire](https://github.com/yunhyuk-choi/gitwire) 를
옆에 나란히 두지 않아도 설치된다(`pyproject.toml` 의 `dependencies` 가 그 레포를
직접 가리킨다). 기반을 함께 고칠 때의 개발용 설치는 아래 「개발」 참조.

클론 없이 바로 설치해 쓸 수도 있고, 그때 **갱신**은 이렇게 한다:

```bash
pip install "gitwire-chat @ git+https://github.com/yunhyuk-choi/gitwire-chat.git"

# 갱신 — 돌고 있으면 먼저 Ctrl+C 로 끈다
pip install --force-reinstall --no-deps   "gitwire-chat @ git+https://github.com/yunhyuk-choi/gitwire-chat.git"
python -m gitwire_chat
```

`--no-deps` 는 바뀌지 않은 전송 계층(gitwire)까지 다시 받지 않게 한다. 갱신 뒤
브라우저는 **강력 새로고침**(Ctrl+Shift+R)한다 — 정적 파일이 캐시돼 있을 수 있다.

옵션:

| 옵션 | 뜻 |
|---|---|
| `--port` | 포트 (기본 8770). 바인드 주소는 `127.0.0.1` 고정이다 — 아래 「보안 모델」 |
| `--home DIR` | 로컬 상태 디렉토리 (기본은 아래 규칙) |
| `--author 이름` | 표시 이름 기본값 |
| `--poll-interval 초` | 폴 주기 (기본 15초) |
| `--no-notify` | OS 알림 끄기 |
| `--open` | 기동 후 브라우저 열기 |

서브커맨드가 하나 있다 — `autostart` (로그인 시 자동으로 띄우기: 등록·해제·상태).
아래 「알림 · 자동 시작」 참조.

### 방 만들기 / 합류하기

1. 사이드바 `＋` → **레포 주소를 넣는다.** 빈 레포면 gitwire 가 방 규약을 심는다.
   클론은 **앱이 알아서** 한다 — 위치도 앱이 정한다(아래 「로컬 상태」). 사용자가
   `git clone` 을 칠 일도, 어디에 둘지 고민할 일도 없다.
2. 같이 대화할 사람을 그 레포의 **collaborator** 로 초대한다.
3. 상대도 자기 컴퓨터에서 이 앱을 띄우고 **같은 주소**를 넣으면 같은 방이 된다.

**레포가 아직 없다면** — 등록 폼의 「레포가 아직 없다 — 만들기 거들기」를 편다.
소유자와 레포 이름을 넣고 확인을 누르면 *무엇이 만들어지는지*(어느 계정에 어떤
이름으로, **비공개**로) 먼저 보여준다. 그 다음은 둘 중 하나다:

* **토큰이 있으면** (`GITWIRE_TOKEN` 등) → 「지금 만들기」 한 번으로 앱을 떠나지
  않고 만든다. 만들어진 주소로 **방까지 이어서 만든다** — 주소를 옮겨 적지 않는다.
* **토큰이 없으면** → GitHub 의 새 레포 폼이 **미리 채워진 링크**를 준다
  (이름·비공개 설정이 채워져 있다). 만들고 돌아와 「만들었다 · 이 주소로 방 만들기」
  를 누르면, 소유자·이름에서 유도한 주소로 방이 만들어진다.

⚠️ 레포 생성은 **계정을 바꾸는 외부 동작**이다. 계획을 보여준 뒤 사용자가 누를
때만 실행하고, 실패하면 사유(이름 중복·권한 부족·토큰 스코프)를 그대로 보여준다.
GitHub 이 아닌 호스트는 거들 수 있는 만큼만 거든다 — GitLab 은 링크만, 모르는
호스트(사내 git 등)는 주소 입력만 받는다.

### 방을 받는 동안 · 실패했을 때

방 등록은 **즉시** 끝나고 클론은 뒤에서 돈다. 그래서 큰 방이나 느린 네트워크에서도
버튼이 멈춰 있지 않다.

* 방은 목록에 **바로 뜨고** "받는 중…" 으로 표시된다. 다 받으면 대화가 저절로
  채워진다(같은 SSE 채널로 상태가 온다).
* 실패해도 **방이 사라지지 않는다.** 그 자리에 사유가 남고 「재시도」가 있다.
  사유는 구분해서 보여준다 — 주소 오류 / 인증 실패 / 없는 레포 / 네트워크.
* 비공개 레포에서 가장 흔한 실패는 토큰이다. 그때는 **어느 환경변수에 무엇을
  넣어야 하는지**까지 안내한다. (GitHub 은 접근 권한이 없는 레포를 "없는 레포"로
  답하므로, 그 안내가 두 경우 모두에 붙는다.)

private 레포라면 토큰이 필요하다. 값은 **저장하지 않는다** — 환경변수 이름만
기억한다.

```bash
# Windows PowerShell
$env:GITWIRE_TOKEN = "ghp_..."
# macOS / Linux
export GITWIRE_TOKEN=ghp_...
```

방마다 다른 토큰을 쓰려면 방 등록 시 "토큰 환경변수" 칸에 다른 이름을 넣는다.

## 로컬 상태는 어디에 쌓이나

방 클론·커서·방 목록은 전부 한 디렉토리 아래에 모인다.

```
<chat_home>/rooms.json                        방 목록 (이 앱 소유)
<chat_home>/installation.txt                  이 설치의 전송 식별자 (gitwire 소유)
<chat_home>/channels/<slug>-<hash>/clone      방 하나의 git 클론
<chat_home>/channels/<slug>-<hash>/cursors    "어디까지 읽었나" (gitwire)
```

`installation.txt` 는 **gitwire 가 만들고 관리한다.** 같은 머신에서 인스턴스를
둘 띄워도(`--home` 을 달리) 서로 다른 전송 식별자를 갖고, 재시작해도 유지된다 —
그래서 "이건 내가 보낸 것인가" 판정이 흔들리지 않는다. 이 앱이 예전에 직접 하던
일인데, 기반이 보장하므로 소비자가 다시 풀지 않는다.

`<chat_home>` 은 이 순서로 정해진다:

1. `--home` 또는 `GITWIRE_CHAT_HOME`
2. **소스 체크아웃**으로 돌고 있으면 `<레포 루트>/chats`
3. 그 외(`pip install` 로 설치한 형태 — 앱 디렉토리가 없다)는 OS 데이터 디렉토리
   (`%LOCALAPPDATA%\gitwire-chat`, `~/Library/Application Support/gitwire-chat`,
   `$XDG_DATA_HOME/gitwire-chat`)

> ⚠️ `chats/` 가 **gitignore 되어 있다는 것이 이 배치의 전제다.** 무시되면 부모
> 레포의 `git status` 에 안 보이고 `git clean -fdx` 도
> `Would skip repository ...` 로 클론을 건너뛴다. 무시되지 **않으면** 즉시
> `embedded git repository` 경고와 함께 gitlink 로 스테이징된다.
> `.gitignore` 의 `chats/` 줄을 지우지 마라. 그리고 그 줄에 **인라인 주석을
> 붙이지 마라** — gitignore 에서 `#` 는 줄 첫 칸에서만 주석이라
> `chats/  # 설명` 은 패턴 전체를 무효화한다.

### (선택) 자격증명 조회 캐시 — `GITWIRE_CHAT_CREDENTIAL_CACHE`

**기본은 꺼져 있다.** 켜려면 초 단위 수명을 준다 (예: `900`).

```bash
# Windows PowerShell
$env:GITWIRE_CHAT_CREDENTIAL_CACHE = "900"; gitwire-chat
# macOS / Linux
GITWIRE_CHAT_CREDENTIAL_CACHE=900 gitwire-chat
```

무엇을 사나 — 백그라운드 폴러가 원격을 볼 때 git 이 왕복마다 OS 자격증명
관리자를 **새 프로세스로** 띄운다. 실측(이 머신 · GitHub private repo, 5회
중앙값) `ls-remote` **1320ms → 1167ms**. 나머지 ~900ms 는 캐시로 지울 수 없는
고정비다(HTTPS 왕복 3회 + 프로세스 기동).

무엇을 파나 — `git-credential-cache` 데몬이 자격증명을 **메모리에** 그 시간 동안
들고 있고, 같은 OS 사용자로 도는 프로세스가 소켓으로 꺼내 쓸 수 있다. 디스크에는
쓰지 않는다. 짧게 잡을수록 노출 창이 좁다.

무엇을 건드리지 않나 — **사용자의 global·system git 설정을 고치지 않는다.**
이 앱이 만든 클론의 `.git/config` 에만 쓰고, 상속된 helper 는 사슬 뒤에 남겨
캐시가 비면 원래대로 동작한다.

⭐ 그리고 이건 **사람이 기다리는 경로가 아니다.** 타임라인 조회는 원격을 아예
보지 않으므로, 이 설정이 줄이는 것은 백그라운드 폴러의 비용뿐이다. 그래서
기본값이 끔이다.

## 알림 · 자동 시작

앱 프로세스는 브라우저와 **무관하게** 방을 폴링한다. 그래서 탭이 닫혀 있거나
숨겨져 있어도 새 메시지를 알고, 그때 OS 알림을 띄운다
(Windows 토스트 / macOS `osascript` / Linux `notify-send`, 전부 실패하면 로그만).
탭이 그 방을 **보고 있으면** 알림을 띄우지 않는다.

### 로그인할 때 자동으로 띄우기

알림이 제 값을 하려면 그 프로세스가 **로그인할 때 이미 떠 있어야** 한다.
명령 한 줄이다 — 안내문을 보고 따라 할 필요가 없다.

```bash
python -m gitwire_chat autostart install --dry-run   # ① 무엇을 어디에 쓸지 먼저 본다
python -m gitwire_chat autostart install             # ② 등록
python -m gitwire_chat autostart status              # 지금 등록돼 있나 · 어디에 · 로그는 어디
python -m gitwire_chat autostart uninstall           # 해제
```

OS 별로 **그 OS 의 정석 수단**을 쓴다. 셸 명령이 아니라 파일 하나를 쓰는 것이
기본이고, 서비스 관리자에게 알려야 하는 곳에서만 한 단계를 더 밟는다.

| OS | 무엇이 만들어지나 | 추가 단계 |
|---|---|---|
| Windows | 시작 폴더(`shell:startup`)의 `gitwire-chat.cmd` | 없음 (파일이 곧 등록이다) |
| macOS | `~/Library/LaunchAgents/com.github.yunhyuk-choi.gitwire-chat.plist` | `launchctl bootstrap` |
| Linux | `~/.config/systemd/user/gitwire-chat.service` | `systemctl --user enable --now` |

지키는 것들:

* **먼저 보여준다.** `--dry-run` 이 쓸 경로와 **파일 내용 전문**을 출력한다.
  실제 등록에서도 같은 것을 보여준 뒤에 쓴다 — 환경을 바꾸는 동작이 조용히
  일어나지 않는다. `--os windows|macos|linux|all` 로 **다른 OS 의 파일도 미리**
  볼 수 있다(미리보기 전용 — 실제 등록은 그 OS 에서만 된다).
* **멱등.** 두 번 등록해도 파일은 하나다. 내용이 같으면 아무것도 쓰지 않고
  "이미 등록돼 있다"고 말한다. 옵션이 바뀌었으면 그 자리를 갱신한다. 해제도
  없으면 없다고 말하고 끝난다.
* **지금 이 인터프리터를 박는다.** venv 로 설치했으면 그 venv 의 인터프리터
  **절대 경로**가 들어간다 — 로그인 셸의 `PATH` 를 믿지 않는다. `--port`·`--home`
  같은 옵션도 등록 시점 값이 그대로 파일에 들어간다.
* **콘솔 창이 뜨지 않는다.** Windows 에서는 같은 디렉토리의 `pythonw.exe` 를
  쓴다(있는지 실제로 확인하고, 없으면 `python.exe` + 최소화로 폴백하며 그 사실을
  보고한다).
* **로그가 남는다.** 백그라운드로 돌면 실패해도 화면에 아무것도 안 남으므로,
  표준출력·표준오류를 파일 하나로 모은다. `status` 가 그 경로를 알려준다.
  (`%LOCALAPPDATA%\gitwire-chat\logs\` / `~/Library/Logs/gitwire-chat/` /
  `$XDG_STATE_HOME/gitwire-chat/logs/`)
* **systemd 가 없는 Linux 에서는 명확히 실패한다.** 조용히 다른 수단으로
  넘어가지 않고, 수동 방법을 안내한다 — 등록됐다고 믿게 만드는 것이 제일 나쁘다.

> ⚠️ Windows 의 시작 폴더에는 감독자가 없다. `uninstall` 은 **다음 로그인부터**
> 뜨지 않게 한다 — 지금 떠 있는 프로세스는 그대로 돈다(작업 관리자에서
> `pythonw.exe` 를 끝내면 된다). macOS·Linux 는 `bootout`/`disable --now` 로
> 그 자리에서 함께 내린다.

**Windows 에서 작업 스케줄러를 쓰지 않는 이유** — 스케줄러에도 "로그온 시 실행"
트리거가 있다. 하지만 등록 수단이 `schtasks`/XML(UTF-16)이라 셸·인코딩 의존이
늘고, 사용자가 눈으로 확인·삭제하기 어렵다. 시작 폴더는 탐색기에서 바로 보이고
파일을 지우면 끝난다. 스케줄러가 주는 추가 능력(지연·조건·재시도)은 "로그인하면
뜬다"는 목적에 필요하지 않다.

#### 수동으로 하려면

자동 등록이 막히는 환경이 있다(정책으로 시작 폴더가 잠긴 경우, systemd 없는
배포판, 읽기 전용 홈 등). 그때는 아래를 손으로 한다 — `autostart install
--dry-run` 이 출력하는 내용을 그대로 붙여 넣으면 된다.

* **Windows** — `Win+R` → `shell:startup` → 아래 내용의 `.cmd` 파일을 넣는다.
  (또는 작업 스케줄러 → 새 작업 → 트리거 "로그온할 때" → 동작에 같은 명령)
  ```bat
  @echo off
  start "" /b "C:\경로\pythonw.exe" -m gitwire_chat --port 8770
  ```
* **macOS** — `~/Library/LaunchAgents/` 에 `.plist` 를 만들고
  `launchctl bootstrap gui/$UID <plist 경로>` (`ProgramArguments` 에
  `python3 -m gitwire_chat`).
* **Linux (systemd --user)** — `~/.config/systemd/user/gitwire-chat.service`
  를 만들고 `systemctl --user enable --now gitwire-chat`.
* **systemd 가 없으면** — 데스크톱 환경의 "시작 프로그램"에 등록하거나
  `~/.xprofile` 에 같은 명령을 백그라운드(`... &`)로 넣는다.

> 등록 파일을 둘 디렉토리는 `--dir`(또는 `GITWIRE_CHAT_AUTOSTART_DIR`)로 바꿀 수
> 있다. 실제 시작 폴더를 건드리지 않고 시험해 보거나 테스트할 때 쓴다.

## 메시지는 어떻게 생겼나

gitwire 봉투와 이 앱의 payload 는 **역할이 겹치지 않게** 나눠 담는다.

| 무엇 | 어디 | 왜 |
|---|---|---|
| 메시지 ID·정렬 키 | 봉투 `id` | 이미 유일하고 정렬 가능하다. 새로 만들 이유가 없다 |
| 표시 시각 | 봉투 `ts` | git 호스트 기준 **공통 시계**. 로컬 시계보다 정확하다 |
| 발행 설치본 | 봉투 `sender` | 전송 식별자(IP 에 가깝다). 표시용이 아니다 |
| 표시 이름 | payload `author` | 한 사람이 프로세스를 둘 쓸 수 있다 |
| 본문 | payload `text` | |
| 답장 대상 | payload `reply_to` | 봉투 `id` 를 가리킨다 |
| 종류·버전 | payload `kind`·`v` | append-only 라 나중에 고칠 수 없다 |

레포에 실제로 쌓이는 파일 한 건:

```json
{"gitwire":1,"id":"records/20260903/20260903T041210032Z-alice@example.com.a3f9c1-f96bb4.json",
 "sender":"alice@example.com.a3f9c1","ts":"2026-09-03T04:12:10.032Z",
 "payload":{"kind":"msg","v":1,"author":"앨리스","text":"안녕"}}
```

## 화면이 지키는 것

* **타임라인을 통째로 다시 그리지 않는다.** 서버는 HTML 을 한 번만 주고, 이후엔
  SSE 로 온 JSON 한 건마다 노드를 만들어 붙이기만 한다. **화면 안에 있는** 노드는
  다시 만들지 않는다(`innerHTML` 을 쓰지 않는다 — 덤으로 XSS 봉쇄).
* **가상 스크롤이다.** 대화가 수천 건이어도 **보이는 만큼만** DOM 에 둔다
  (실측: 2000건 대화에서 DOM 노드 9~18개, 스크롤해도 그대로).
  엔진은 [@tanstack/virtual-core](https://tanstack.com/virtual)(MIT)를 레포에
  **벤더링**해 쓴다 — 빌드 단계가 없고 CDN 도 쓰지 않으므로 오프라인에서도 뜬다.
  * **높이는 실측한다.** 메시지 길이가 제각각이라 고정 높이 가정이 성립하지 않는다
    (`measureElement`). 창 크기가 바뀌면 다시 잰다.
  * 화면 밖 노드를 걷어내는 것은 **정상 동작**이다. 그래서 "리렌더 사고"와 구분해
    센다 — `recycled`(정상) vs `rebuiltInView`(**항상 0**이어야 하는 사고).
    테스트에는 일부러 사고를 내는 **대조군**이 있어 이 구분이 살아 있음을 확인한다.
  * 검색은 영향을 받지 않는다 — 서버가 **레코드 파일**을 뒤지므로 DOM 에 없는
    과거도 그대로 찾는다.
  * **가상화가 안 되면 결함으로 드러난다 — 조용히 느려지지 않는다.**
    한때 여기에 격하(degrade, 전부 그리기 폴백)가 있었지만 걷어냈다. 가상 스크롤은
    성능 때문에 붙인 기능이고, 폴백은 그 기능이 **빠진 채로** 앱이 돌게 만든다 —
    다음에 벤더를 갱신하다 또 깨지면 아무도 모르고 느린 채팅을 쓴다. 지금은
    상태줄·대화 자리·콘솔 **세 곳**에 결함이 뜨고, 그 실패는 **타임라인 모듈에만
    갇힌다**(사이드바·＋·검색은 그대로 동작한다 — 아래 「화면은 모듈로 갈라져 있다」).
* **조용한 실패는 금지다.** 스크립트에서 처리되지 않은 예외가 나면 상태줄에 뜬다
  (`error` · `unhandledrejection`). 이 앱을 쓰는 사람은 개발자 콘솔을 열지 않는다 —
  콘솔에만 남는 예외는 "아무 일도 안 일어나는 앱"과 구분되지 않는다.
  그 안내는 일상적인 상태 갱신으로 지워지지 않는다.
* **방 상태가 화면에 있다.** 받는 중·실패(사유)·재시도가 방 목록과 대화 자리에
  같이 보인다. 상태는 방 목록을 미는 기존 SSE 이벤트에 얹혀 온다(새 배관 없음).
* **위로 스크롤하면 과거가 이어 붙는다.** 페이지 버튼이 아니다. 위 끝에 가까워지면
  (`IntersectionObserver`) 다음 쪽을 자동으로 가져와 앞에 끼운다.
  * 끼우기 **전** 높이를 재고 늘어난 만큼 `scrollTop` 을 보정한다 → **읽던 자리가
    튀지 않는다.** (`overflow-anchor` 는 브라우저마다 달라 믿지 않고 꺼 둔다.)
  * 로딩 중에는 관찰을 끊는다 → 트리거가 연달아 발화해도 **요청은 한 번**이다.
  * 맨 위에 닿으면 조용히 멈춘다("대화의 시작").
* **보낸 말은 즉시 뜬다 (낙관적 업데이트).** 서버 응답을 기다리지 않는다 —
  Enter 를 누른 순간 말풍선이 흐리게("보내는 중…") 붙고, 서버가 실제 레코드를
  주면 **같은 노드의 키만** 진짜 봉투 ID 로 갈아 끼운다(노드를 다시 만들지
  않는다 — `rebuiltInView` 는 여전히 0). 실패하면 그 자리에 **"전송 실패" 와
  재시도**가 붙고 **글은 말풍선 안에 그대로 남는다**(입력칸으로 되돌리면 같은
  글이 두 곳에 생긴다). 응답보다 폴링(SSE)이 먼저 도착해도 같은 말이 두 줄로
  뜨지 않는다.
* **위로 읽는 중에 온 새 메시지가 자리를 뺏지 않는다.** 맨 아래에 붙어 있을 때만
  따라 내려가고, 위에 있으면 "새 메시지 N건 ↓" 표시만 띄운다.
* 좁은 창에서는 방 목록/대화가 한 화면씩 전환된다.

## 화면은 모듈로 갈라져 있다

`static/app.js` 는 **진입점 한 장**이고, 화면은 `static/js/` 의 모듈들이 나눠
소유한다. 각 모듈이 **자기 DOM 영역과 자기 상태만** 갖고 남의 노드를 만지지 않는다.

| 모듈 | 소유하는 화면 | 소유하는 상태 |
|---|---|---|
| `roomlist.js` | `#rooms` · 제목 · `#back` · `#room-trouble*` | 방 목록, 현재 방 |
| `addroom.js` | `#add-room` 폼 · `#toggle-add` | 표시 이름 사본 |
| `newrepo.js` | `#new-repo-*` | 만들기 계획 |
| `timeline.js` | `#timeline` · `#messages` · `#older-sentinel` · `#jump-latest` | 대화 모델·가상화·커서·보류 항목 |
| `message-node.js` | 메시지 **한 건**의 DOM | (없음 — 순수 변환) |
| `composer.js` | `#composer` · `#text` · `#author` · `#reply-chip` | 답장 대상, 표시 이름, 전송 시도 |
| `search.js` | `#search-*` | 현재 방 |
| `stream.js` | SSE 연결 · `#refresh` | 연결, 현재 방 |
| `presence.js` | (DOM 없음) 가시성 | 현재 방 |
| `statusbar.js` | `#status` | 사라지면 안 되는 안내 |
| `bus.js` · `api.js` · `dom.js` | (없음 — 도구) | (없음) |
| `boot.js` | 조립소 | 모듈 핸들, 실패 목록 |

모듈끼리는 **이벤트(`bus.js`)** 로만 이야기한다 (`room:switch` · `rooms:list` ·
`message:new` · `draft:add|settle|fail|retry` · `reply:to` · `repo:ready` …).
도구(dom·api·status)만 명시적으로 주입한다.

무엇이 좋아지나 — 두 가지가 **구조에서** 나온다:

* **격리.** 한 모듈이 초기화에서 던져도 그 모듈만 실패한다. 예전에는 1000줄짜리
  통짜 IIFE 여서 가상 스크롤 생성자 하나가 터지면 `+` 버튼·방 목록·검색이 전부
  죽었다 — 가상화는 메시지 리스트 하나에만 거는 것인데도. 배선을 앞으로 옮기는
  것은 고장 지점을 뒤로 민 것일 뿐 구조는 그대로였다.
  (실패는 삼키지 않는다: 상태줄·콘솔·`__chat.failures` 에 남는다.)
* **리렌더 국소성.** 메시지 노드를 만드는 곳이 `message-node.js` 하나이고 모델을
  가진 곳이 `timeline.js` 하나다. 그래서 "타임라인을 다시 그리지 않는다"가 전역
  규율로 *감시*할 일이 아니라 소유 관계의 결과가 된다. `rebuiltInView` 카운터는
  남아 있지만 이제 **회귀 감지기**지 규율을 지키는 수단이 아니다.

진입점은 `<script type="module">` 이고 벤더 엔진을 `import` 로 직접 가져온다.
예전에는 인라인 모듈이 `window` 에 엔진을 담아 두고 classic 스크립트가 그것을
집어갔는데, "실렸나 / 그때 실렸나"가 실제 사고 지점이었다. 빌드 단계는 여전히
없다 — 브라우저가 파일을 그대로 받는다.

## 개발

```bash
pip install -e .            # 앱 (gitwire 는 GitHub 에서 받아온다)
pip install -e ../gitwire   # 기반도 함께 고칠 때만 — 로컬 체크아웃으로 갈아끼운다
python -m pytest -q
```

두 번째 줄이 앞서 설치된 `gitwire` 를 로컬 체크아웃으로 덮어쓴다. 기반 API 를
바꾸면서 소비자를 함께 고칠 때 이 형태로 쓴다. 되돌리려면
`pip install --force-reinstall "gitwire @ git+https://github.com/yunhyuk-choi/gitwire.git"`.

핵심 검증은 **앱 인스턴스 두 개가 로컬 bare 레포를 방으로 삼아 실제 git 으로
대화하는 것**이다(`tests/test_two_instances.py`). 대역이 아니라 진짜 git 이다 —
clone·push·커서 영속은 흉내내면 아무것도 증명하지 못한다. 나머지 테스트는
gitwire 채널을 주입 가능한 대역으로 갈아끼워 네트워크 없이 돈다.

### 프런트엔드는 세 층으로 검증한다

한 층으로는 부족하다는 것을 **비싸게 배웠다.** stub DOM 테스트가 22/22 로 통과하는
동안 앱은 브라우저에서 완전히 죽어 있었다(모든 버튼 무반응). 그래서 층을 나눈다 —
서로를 대체하지 않는다.

| 층 | 무엇을 본다 | 못 보는 것 |
|---|---|---|
| `node --check` + stub DOM (`tests/js/`, `tests/test_frontend.py`) | `createApp()` 을 **그대로 import 해** stub 런타임(document·fetch·EventSource)을 주입하고 구동한다 — 프로덕션 진입점이 하는 일과 같은 모양이라 하네스와 실물이 어긋나지 않는다. **DOM 조작 횟수와 노드 동일성**을 센다 — "리렌더가 없다"를 주장이 아니라 수로 확인한다. 가상 스크롤 엔진은 대역이 아니라 **벤더링된 진짜**를 구동한다 | Node 안에서 돈다(브라우저에만 없는 전역), 로딩 순서를 건너뛴다, `index.html` 을 안 읽는다 |
| 벤더 원문 검사 (`tests/test_vendor_assets.py`) | 브라우저로 가는 JS 에 **Node 전용 전역**(`process` · `require()` · `module.exports` · `__dirname` …)이 하나도 없다. 출처·LICENSE·버전 표기도 본다 | 실행하지 않는다 — 문법·동작은 안 본다 |
| **브라우저 연기 테스트** (`tests/test_browser_smoke.py`) | 진짜 헤드리스 브라우저로 페이지를 연다. **콘솔에 `Uncaught` 가 하나라도 있으면 실패**, 그리고 브라우저가 **`/api/rooms` 를 실제로 불렀나**(= 배선까지 갔나) | 느리다. 세밀한 카운팅은 못 한다 |

브라우저 연기 테스트가 상태코드를 근거로 쓰지 않는 이유: 앱이 완전히 죽어 있던
그때도 페이지 응답은 **200 이었다.** 200 은 아무것도 증명하지 않는다.

크로미움 계열 브라우저(Edge·Chrome·Chromium)를 PATH 와 각 OS 의 관례적 설치
위치에서 찾는다. **없으면 SKIP** 한다 — 리눅스 CI·맥에서 스위트가 깨지지 않는다.
SKIP 사유는 `-ra`(기본 `addopts`)로 매 실행 요약에 뜬다. 경로를 직접 주려면
`GITWIRE_CHAT_BROWSER=/path/to/msedge`.

손으로 같은 것을 보고 싶으면 (앱이 `<포트>` 에 떠 있을 때):

```bash
EDGE="/c/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"
"$EDGE" --headless=new --disable-gpu --no-sandbox --user-data-dir=/tmp/edge-smoke   --enable-logging=stderr --log-level=0 --virtual-time-budget=8000   --dump-dom "http://127.0.0.1:<포트>/" > dom.html 2> console.txt
grep -iE 'CONSOLE|Uncaught' console.txt      # 여기에 Uncaught 가 있으면 앱은 죽은 것이다
```

### 가상 스크롤 엔진을 올릴 때

`static/vendor/tanstack-virtual-core/` 에 npm 배포본의 `dist/esm/*` 와 `LICENSE` 를
복사한다(빌드 단계 없음). ⚠️ **그대로 복사하면 안 된다** — 상류는 번들러가 있다는
전제로 `NODE_ENV` 환경변수 참조를 남겨 두고, 브라우저에는 그 전역이 없다. 절차와
경위는 `static/vendor/tanstack-virtual-core/VENDORING.md` 에 있고,
`tests/test_vendor_assets.py` 가 빠뜨림을 잡는다.

파일은 UTF-8(BOM 없음)·LF 로 쓴다. 코드·주석·UI 문구는 한국어다.

라이선스는 MIT (`LICENSE`).

## 보안 모델 · 설계상 그런 것

한계처럼 보이지만 **의도한 설계**인 것들이다. 쓰기 전에 알고 있어야 한다.

* **루프백에만 바인드한다 — 그래서 인증이 없다.** `127.0.0.1:8770` 에서만 뜨고
  바꿀 수 있는 옵션이 없다. 내 컴퓨터에서 나만 쓰는 앱이라는 전제 위에서
  로그인·세션·CSRF 를 전부 생략했다. 밖에서 접근해야 한다면 그건 이 앱이 아니라
  앞단(SSH 터널·인증 붙은 리버스 프록시)이 책임질 일이다.
* **레포 접근권이 곧 참여권이다.** 방 = git 레포이므로 그 레포에 접근할 수 있는
  사람이 참가자다. per-message ACL 은 없고, 나중에 초대한 사람도 과거 대화를
  전부 본다 — 팀 채팅에서 흔한 동작이며, git 히스토리를 그대로 쓰는 이 구조의
  자연스러운 귀결이다.
* **대화가 쌓이면 레포도 커진다.** 메시지 한 건 = 파일 한 건 = 커밋이다. 채팅
  기록이 로컬에 쌓이는 것 자체는 채팅 앱의 정상 동작이고, 정말 줄이고 싶으면
  `gitwire compact`(파괴적) 또는 shallow clone 이 있다.
* **검색은 레코드를 읽어서 찾는다.** 인덱스를 두지 않았다. 파일 안을 찾는 일이
  원래 그렇고, 방 하나가 사람이 쓰는 대화인 한 이 방식으로 충분하다.
* **레포 생성은 사람이 누를 때만 한다.** 토큰이 있어도 조용히 만들지 않는다 —
  무엇이 만들어지는지(소유자·이름·공개범위) 보여주고, 누른 뒤에만 만든다.

## 정직한 한계

이 앱이 **못 하는 것**들이다. 쓰기 전에 반드시 읽어라.

* **실시간이 아니다.** 지연 = 폴 주기다. 기본 15초면 상대가 보낸 말이 최악
  15초 + pull 시간 뒤에 뜬다. 주기를 줄이면 그만큼 호스트에 요청이 늘어난다
  (rate limit 주의). 내가 보낸 말은 낙관적 업데이트로 즉시 보이지만, 그건
  화면일 뿐 상대에게 도착한 시점과는 다르다.
* **타임라인 조회는 원격을 보지 않는다 — 그래서 "마지막 폴 시점" 기준이다.**
  대화 기록은 이미 로컬 클론에 있고, 신선도는 폴러가 맡는다. 방을 여는 순간에는
  **화면을 막지 않고** 백그라운드로 한 번 더 당기며(새 것은 SSE 로 뒤따라 붙는다),
  「지금 당겨오기」 버튼은 언제나 즉시 원격을 본다. 이 설계 이전에는 조회 한 번이
  `git ls-remote` 왕복(실측 1.3초)을 매번 물고 있어서 **최근 50건 조회가
  1.4~2.9초** 였다. 실측 before/after (진짜 GitHub 원격, 5회 중앙값):
  최신 쪽 **1463ms → 51ms**, 위로 페이징 **1359ms → 49ms**.
* **진짜 push 알림이 없다.** 서버가 우리를 깨우지 않는다. 전부 폴링이라
  OS 알림도 폴 주기만큼 늦게 뜬다.
* **메시지 삭제가 사실상 안 된다.** append-only 다. 지우려면 히스토리 재작성
  (`gitwire compact`)이 필요하고 그건 모든 참가자에게 파괴적이다.
* **참가자 사이의 순서는 시계 보정 오차만큼 흔들린다.** 타임스탬프 자체는
  **밀리초** 해상도이고(`20260903T041210032Z`), 한 사람이 보낸 메시지들은 그
  해상도로 순서대로다(같은 밀리초에 두 건을 내거나 그 사이 시계가 뒤로 조정되면
  아래의 ID 규칙으로 갈린다). 뒤집힐 수 있는 것은 **서로 다른 참가자의 메시지가
  거의 동시에 발행됐을 때**뿐이다 — 공통 시계(git 호스트 `Date` 헤더 기준)의
  잔여 오차가 대략 ±(0.5 + RTT/2)초라서, 그 안에서 앞뒤가 바뀔 수 있다.
  타임스탬프가 같으면 메시지 ID 로 갈리는데, 그 순서는 **모든 참가자에게 동일**
  하다(ID 사전식 정렬 = 표시 순서). 즉 화면이 사람마다 달라지지는 않는다.
* **여러 명이 초 단위로 쏟아붓는 용도가 아니다.** 동시 발행이 잦으면 push 경합
  재시도가 늘어난다. 정확성은 유지되지만 느려진다.
* **방에 처음 합류할 때 과거를 전부 내려받는다.** 화면에 그리는 것과 서버에서
  읽는 것은 이미 "본 만큼"이지만(가상 스크롤 + keyset 페이징), *클론*은 여전히
  전량이다. 부분 클론(`--filter=blob:none`)으로 줄여 보려다 측정에서 손해로
  나와 넣지 않았다 — 근거는 gitwire README 「부분 클론을 쓰지 않는 이유」.
* **아주 오래된 대화로 계속 거슬러 올라가면 모델이 커진다.** DOM 노드 수는
  상수로 유지되지만(가상 스크롤), 불러온 메시지 자체는 메모리에 쌓인다.
  방을 바꾸거나 새로고침하면 비워진다.
* **한 모듈이 죽으면 그 영역은 정말로 안 된다.** 격리는 "나머지가 산다"는
  뜻이지 "고장이 사라진다"는 뜻이 아니다. 타임라인이 서지 못하면 대화는 보이지
  않고 그 자리에 결함이 뜬다 — 느린 대체 경로로 감추지 않는다(그게 의도다).
* **브라우저 검증은 연기 감지기지 E2E 가 아니다.** 크로미움 계열 한 종류를
  헤드리스로 열어 **처리되지 않은 예외**와 **첫 배선**(`/api/rooms` 호출)만 본다.
  사람이 클릭·입력하는 흐름 전체, 그리고 Firefox·Safari 는 자동 검증 범위 밖이다.
  이 정도로도 "앱이 통째로 죽었는데 테스트는 전부 통과"는 다시 일어나지 않는다.
